知识点 02 · 对应课件 AJAX 与 XMLHttpRequest

不刷新页面，也能把远程数据插进 DOM

上一节解决了「数据长什么样」，这一节解决「怎么把它拿回来」。 我们用最老、最底层、也最容易被考到的 XMLHttpRequest 发起请求， 并重点讲清一件事：什么时候走 onerror，什么时候只是 status 不对。

必考 客户端-服务器 readyState / status onload / onerror 回调地狱
1.1

一次「请求-响应循环」request / response

客户端（你的手机、笔记本、浏览器标签）向服务器发出一个请求； 服务器接到后校验参数、执行业务逻辑、读写数据库，再把结果包成响应送回来； 客户端拿到响应后渲染 HTML/CSS 并执行 JS。整个过程里，页面不需要整页刷新。

客户端

发起请求、渲染界面

浏览器只能展示与交互，它手里没有权威数据，所有内容都得向服务器要。

服务器

校验 + 执行 + 返回

唯一的数据权威来源：数据存在这里，业务规则也由这里裁决。

响应

页面片段或数据

响应可以是 HTML，也可以只是一份 JSON 数据，由浏览器再拼成最终界面。

延迟 vs 吞吐：两端关心的不是同一件事

视角 关心的指标 含义 典型优化
客户端 延迟 latency 单次请求快不快：从发出到看到结果花了多久 缓存、CDN、减少请求数
服务器 吞吐 throughput 单位时间能扛多少请求：每秒能处理多少 QPS 加机器、加索引、连接池
定义
AJAX 不是一个具体技术，而是一组技术的集合： 它指的是「不整页刷新就能局部更新页面」的这一类做法。 把名字拆开看：Asynchronous（异步，不阻塞页面）+ JavaScript（发起请求的语言）+ XML（早期用的数据格式，今天基本已被 JSON 取代）。 名字里的 XML 只是历史包袱，与今天实际用什么格式无关。
1.2

XMLHttpRequest 是什么the built-in request object

XMLHttpRequest（简称 XHR）是浏览器内置的 API， 不装任何库就能用。你创建一个请求句柄，它就代表一次请求；请求默认异步， 发出后主线程继续运行，等服务器回话时再通过回调通知你。

它今天已经不那么流行了（课件原话是 fallen out of favour），新代码一般直接用 fetch。但你必须看得懂它 —— 因为大量遗留代码、老教程、老面试题里到处是它，而且它的 readyState / status 心智模型在 fetch 时代依然成立。

01

默认异步

xhr.open() 不传第三个参数就是异步：请求发出后主线程不等待，继续往下跑。

02

靠回调定制行为

主要是 xhr.onload（拿到响应）与 xhr.onerror（网络失败）两个回调。

03

靠状态码报错

HTTP 层面的失败（404、500）会落在 xhr.status 上，得你自己判断。

1.3

readyState 与 statustwo different numbers

XHR 会同时维护两个很容易混淆的数字：readyState 描述 请求走到哪一步了，status 描述 服务器是怎么回答的。两者必须各自检查。

readyState：一次请求的生命周期

值 常量名 含义
0UNSENT尚未调用 open()
1OPENED已调用 open()，请求已建立
2HEADERS_RECEIVED已收到响应头（还没拿到响应体）
3LOADING正在下载响应体
4DONE完成，响应体已经收全

所以在 readystatechange 里，只有 readyState === 4 的时候，responseText 才是完整的、可以读的。还要注意：只要 HTTP 响应回来了，readyState 就会走到 4， 哪怕是 404 —— 因为 4 只代表「通信结束」，不代表「成功」。

status：服务器是怎么回答的

状态码 归类 含义
200成功请求正常完成，响应体就是你要的数据
4xx客户端错误你把 API 用错了：404 资源不存在、400 参数不对、401 没登录
5xx服务端错误服务器自己内部出错：500、502、503
区分
readyState === 4 说的是「通信结束了」； status === 200 说的才是「业务成功了」。 两个数字都要各自检查一次，缺一个都会写出 bug。
1.4

★ 错误处理的分工expected vs unexpected

这是这一页最重要、也最容易被考倒的一点：要把错误分成两类，分别处理。

预期内的错误 · Expected

服务器已经正常回话

认证失败、参数错误、资源不存在……服务器已经回话了，只是这次业务失败。 它会正常走 onload，你必须自己检查 xhr.status。

预期外的错误 · Unexpected

根本没拿到响应

网络不通、连接突然中断、请求超时……这时才会进入 xhr.onerror， 此时 xhr.status 是 0。

最容易错
4xx / 5xx 不会触发 onerror，fetch 也一样。 onerror 只负责网络层的失败； 只要服务器回了 HTTP 响应（哪怕是 404、500），对 XHR 来说这也是一次「成功通信」， 一定会走 onload。这条规则后面几节还会用到。
策略
处理「预期外错误」（网络抖动、超时）时的常见策略是重试 + 指数退避： 失败后等一个越来越长的时间再重试（如 0.5s → 1s → 2s → 4s）， 既能扛过短暂抖动，又不会一窝蜂重试把服务器再打垮，也不会让用户对着空白页面干等。
1.5

完整示例代码a complete example

下面把整条链路串起来：创建句柄 → open() → 在 onload 里按 status 分支 → 在 onerror 里处理网络失败 → send()。 另外加了一段本地兜底：远程失败时改读同构的本地 JSON，保证演示在断网时也能出结果。

javascript demo/xhr-basic.js 

// ① 创建一个请求句柄
const xhr = new XMLHttpRequest();

// ② 配置请求：GET，默认异步（第三个参数省略即为 true）
xhr.open('GET', 'https://jsonplaceholder.typicode.com/users');

// ③ 定制回调：load = 收到响应；error = 网络层失败
xhr.onload = function () {
  // 关键：onload 只代表「通信结束」，不代表「业务成功」
  if (xhr.status >= 200 && xhr.status < 300) {
    const users = JSON.parse(xhr.responseText);   // 响应体是字符串
    render(users);                                // 把数据渲染进页面
  } else {
    // 4xx / 5xx：属于「预期内错误」，onerror 根本不会来
    console.warn('业务失败，HTTP ' + xhr.status);
    loadFallback();                               // 改用本地兜底数据
  }
};

xhr.onerror = function () {
  // 网络层失败：连不上 / 中断 / 超时，此时 status 是 0
  console.error('网络失败，status = ' + xhr.status);  // 0
  loadFallback();
};

// ④ 真正把请求发出去
xhr.send();

// ⑤ 本地兜底：远程失败时改读结构相同的本地 JSON
function loadFallback() {
  const fb = new XMLHttpRequest();
  fb.open('GET', 'assets/fallback-users.json');
  fb.onload = function () {
    if (fb.status === 200) render(JSON.parse(fb.responseText));
  };
  fb.send();
}

function render(users) {
  const box = document.querySelector('#user-list');
  box.innerHTML = users.map(function (u) {
    return '<div class="list-item">' + u.name + '</div>';
  }).join('');
}
要点
注意 onload 里那句 if： 它判断的是 xhr.status，而不是「有没有触发 onload」。 因为 404 也会触发 onload，只有把 status 拿出来看，才知道这次到底是成是败。
1.6

回调地狱与规避avoid callback hell

当异步操作要按顺序串起来（先拿用户 → 再拿订单 → 再拿详情）， 每一层都得在回调里再写一个回调，代码就向右不断「长出一棵圣诞树」， 这就是回调地狱（callback hell）。 它的成因通常不是技术问题，而是多人协作 + 临时决策： 每个人都顺手往里塞一层，最后没人敢动。

✗ 嵌套写法：越写越深
getUser(1, function (user) {
  getOrders(user.id, function (orders) {
    getDetail(orders[0].id, function (detail) {
      render(detail, function () {
        // 出错时根本不知道该在哪一层处理
      });
    });
  });
});
✓ 扁平化写法：具名函数，一层一个职责
function onDetail(detail) { render(detail); }
function onOrders(orders) { getDetail(orders[0].id, onDetail); }
function onUser(user)    { getOrders(user.id, onOrders); }

getUser(1, onUser);   // 读起来是从上往下的直线

三条规避原则

  • 回调用具名函数：把匿名回调提出来起个名字，扁平（flat）永远优于嵌套（nested）。
  • 遵守 SRP 与 DRY：一个函数只做一件事（单一职责）；重复逻辑抽出来复用（不要重复自己）。
  • Lambda 只用于一行代码：像 users.map(u => u.name) 这种一行箭头函数很清晰；一旦超过一行，就该提成具名函数。

后面几节会看到，Promise 与 async / await 正是为了把这种「层层嵌套」重新拉直成一条从上往下的线。

小结

这一节要带走的三句话takeaways

01

客户端不持有权威数据

数据在服务器上，客户端只负责发起请求、渲染响应；别把业务真相寄托在前端内存里。

02

readyState 到 4 之后才有内容

只有 readyState === 4 时 responseText 才完整可读；但 4 只代表通信结束，不代表成功。

03

4xx / 5xx 走 status，不走 onerror

onerror 只管网络层失败（status = 0）；服务器只要回话就走 onload，成败靠自己看 status。
