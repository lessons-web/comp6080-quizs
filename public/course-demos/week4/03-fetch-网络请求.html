fetch 会 resolve，但不代表请求成功

上一节的 XMLHttpRequest 什么都得自己来：手动 open / send、 两个回调、自己读 responseText、自己判状态码。 ES2015 给了我们 fetch：一个 Promise 化的原生请求 API。 它更好写，但有一个必须记住的坑 —— 它会「对 HTTP 错误装作没看见」。

必考 fetch Response res.ok AbortController
1.1

为什么会有 fetchpromise-based fetching

上一节用 XHR 拉一个接口，要写一串样板代码：open、send、 挂 onload 与 onerror 两个回调， 还要手动 JSON.parse(xhr.responseText)、手动判断 status 是否在 200 段。 繁琐，而且很容易漏掉某一步。

ES2015 引入的 fetch 是浏览器原生的、Promise-based 的 JS API， 专门用来下载远程资源。它把「发起请求」这一步变成一个 Promise， 后面既可以接 .then 链，也可以配 async / await（下一节细讲）。 左右两段代码做的是同一件事，对比一下就看得出差别。

✗ XHR：命令式，一堆手动步骤

// 手动 open / send，两个回调，自己 parse、自己判状态码
const xhr = new XMLHttpRequest();
xhr.open('GET', '/api/users');
xhr.onload = function () {
  if (xhr.status >= 200 && xhr.status < 300) {
    const data = JSON.parse(xhr.responseText);  // 自己 parse
    render(data);
  } else {
    showError(xhr.status);                      // 自己判状态码
  }
};
xhr.onerror = function () { showError('网络错误'); };
xhr.send();
✓ fetch：Promise 化，一条链读完

// 发起请求就是拿到一个 Promise，之后接 then 就行
fetch('/api/users')
  .then(res => res.json())     // 读响应体
  .then(data => render(data))  // 拿到数据
  .catch(err => showError(err));
// 状态码仍然要自己判，见 1.3
1.2

fetch 的基本形态it resolves to a Response

fetch(url) 返回一个 Promise。一定要记住它 resolve 出来的是什么： 不是数据本身，而是一个 Response 对象 —— 它描述的是「这次 HTTP 交互」，里面有状态码、响应头，以及一条还没读的响应体流。

想拿到 JSON 数据，必须再等一次：调用 res.json() （返回的是纯文本就用 res.text()）。 原因很简单：响应体是流，只能读一次，读的动作是异步的。

javascript demo/fetch-basic.js 

// 最短可用形态：两次 then
fetch(url)
  .then(res => res.json())   // 第 1 步：把响应体读成 JSON（异步）
  .then(data => console.log(data))
  .catch(err => console.error(err));

// 等价的 async / await 写法（下一节细讲）
const res  = await fetch(url);   // res 是 Response，不是数据
const data = await res.json();   // 这一步才拿到数据
补充
fetch(url, options) 的第二个参数控制请求方式： method（GET / POST …）、headers、 body、认证信息（credentials）以及 mode / CORS 相关设置。不传就是最简单的 GET。右边演示 B 专门演示它。
1.3

最关键的一条：只在网络失败时 reject404 is not an error

这一条是本页的核心，也是最容易在作业里踩的坑。fetch 的 Promise：

  • 收到任何 Response 就 resolve —— 哪怕 HTTP 状态码不是 200。
  • 只有网络层面失败才 reject —— 比如断网、域名解析不了、请求被 CORS 拦下。

也就是说：404、500 这些统统会 resolve， 根本不会进你的 catch。所以服务器告诉你「找不到」， 而 fetch 却像什么都没发生一样把 Promise 标记为成功。

因此必须自己判：if (!res.ok) throw new Error(...)。 res.ok 等价于 status >= 200 && status < 300。

口诀
fetch 不认 404，自己判 res.ok。 拿到 Response 之后、读 body 之前，先写这一行。
✗ 不判 res.ok：把 404 当成功继续渲染

// 404 时 Promise 依然 resolve，于是这里继续往下走
const res = await fetch('/api/nonexistent');
const data = await res.json();   // 得到的是空对象 {}
renderUsers(data);               // 拿错误当数据渲染 → 用户看到空白页
// catch 永远不会被触发！
✓ 判了 res.ok：明确抛错，走到 catch

try {
  const res = await fetch('/api/nonexistent');
  if (!res.ok) {
    throw new Error('HTTP ' + res.status);  // 主动抛错
  }
  renderUsers(await res.json());            // 只有 OK 才读 body
} catch (err) {
  showError(err);                           // 404 在这里被接住
}
1.4

Response 对象上有什么inspect the response

既然 fetch 交给你的是 Response， 那就要熟悉它上面能看的东西。下面是排查问题时最常用的一批。

属性 / 方法 含义
res.status 数字状态码（200 / 404 / 500 …），HTTP 层面的结果
res.statusText 状态码对应的文本，如 OK / Not Found
res.ok 布尔值，status >= 200 && status < 300 时为 true
res.headers.get('content-type') 读响应头，据此判断返回的是 JSON 还是 HTML
res.url 实际发生的请求地址（跟随重定向之后的最终地址）
res.redirected 是否发生过重定向
res.json() 把响应体读成 JSON 对象（异步，返回 Promise）
res.text() 把响应体读成纯文本（异步，返回 Promise）
res.clone() 克隆一份 Response，用于确实需要读两次的场景
注意
响应体只能读一次。 调用过 res.json() 之后，再调 res.text() 会抛出 TypeError: body stream already read。 如果确实需要读两遍（比如既想解析又想留原始文本），必须先克隆： const copy = res.clone();，两份各读一次。右边演示 B 的第二个按钮会复现这个报错。
1.5

与 XMLHttpRequest 的取舍xhr vs fetch

fetch 更现代，但 XHR 并没有「过时到不能用」。做选择前，先看清它们在几个关键维度上的差异。

维度 XMLHttpRequest fetch
语法可读性 命令式：open / send + 多个回调 Promise 链 / async-await，更直观
老浏览器支持 极好（很老的 IE 也支持） 现代浏览器才有，兼容老环境要 polyfill
上传 / 下载进度 原生支持 onprogress 需配合 Streams API，学习曲线陡
可取消性 直接 xhr.abort() 需要 AbortController + signal
Promise 原生支持 没有，要自己包一层 天生返回 Promise
结论
新项目用 fetch + async/await；读老代码时你要认识 XHR。 进度条、需要直接 abort 的场景，XHR 反而省事；其余大多数接口请求，fetch 都更清爽。
1.6

一段健壮的 fetch 封装robust wrapper

把前面几条拼起来，就得到一个可以在项目里直接用的封装：自己判 res.ok、 用 try / catch 兜住错误，再用 AbortController 做一个超时。

javascript demo/fetch-robust.js 

async function fetchJSON(url, options = {}) {
  const { timeout = 5000 } = options;
  const controller = new AbortController();
  const timer = setTimeout(() => controller.abort(), timeout);

  try {
    // ① 网络错误才会 reject；404 / 500 会照常 resolve
    const res = await fetch(url, { signal: controller.signal });

    // ② 关键一步：自己判状态码是否在 200~299
    if (!res.ok) {
      throw new Error('HTTP ' + res.status + ' ' + res.statusText);
    }

    // ③ 状态码 OK 之后才读取响应体（响应体只能读一次）
    return await res.json();
  } catch (err) {
    // ④ 区分「超时被中断」与其它错误
    if (err.name === 'AbortError') {
      throw new Error('请求超时（>' + timeout + 'ms），已中断');
    }
    throw err;                 // 网络错误 / 状态码错误原样抛出
  } finally {
    clearTimeout(timer);       // 无论成败都要清理定时器
  }
}
用法
调用时只要 try { const data = await fetchJSON(url); } catch (err) { … }， 无论是 404、500 还是超时，都会统一进入 catch —— 这才是符合直觉的「失败」。

这一节要带走的三句话takeaways

01

fetch 只在网络失败时 reject

收到任何 Response 就 resolve，哪怕状态码是 404 或 500；只有断网之类的网络错误才进 catch。

02

res.ok 必须自己判

拿到 Response 后先写 if (!res.ok) throw …，再决定要不要读 body。

03

响应体只能读一次

res.json() 之后再读会抛错；确实要读两遍就用 res.clone()。
