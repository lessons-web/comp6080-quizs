async / await：写起来像同步，本质还是 Promise

上一节我们用 then / catch 编排 Promise。这一节换成 async / await，代码一下子变得像同步：从上往下读，就是执行顺序。 但要记住一句话 —— 它没有把异步变成同步，只是把异步写得更像同步， 最大的实际收益是错误处理重新回到 try / catch。

必考 async / await 协程 coroutine try / catch / finally 串行 vs 并行
1.1

三种写法的演进callback → promise → async/await

同一个「取数据 → 渲染」逻辑，历史上一共有三种写法。它们能力完全等价， 差别只在可读性：写法一变，错误处理的形状也跟着变。

① 回调（callback）

javascript demo/three-styles.js 

// 错误是第一参数，必须每次手动判断
getData(url, function (err, data) {
  if (err) {
    console.error('出错了：', err);
    return;
  }
  render(data);
});

② Promise 链

javascript demo/three-styles.js 

// 错误集中到链条末尾的 catch
getData(url)
  .then(function (data) {
    render(data);
  })
  .catch(function (err) {
    console.error('出错了：', err);
  });

③ async / await

javascript demo/three-styles.js 

// 像同步一样从上往下写，错误回到 try / catch
async function main() {
  try {
    const data = await getData(url);
    render(data);
  } catch (err) {
    console.error('出错了：', err);
  }
}
main();
一句话
三种写法能力等价，演进方向是「可读性」，不是「能力」。 async / await 底下跑的还是 Promise，只是把 .then 藏了起来，换来了「顺序阅读」和「统一错误处理」。
1.2

两条核心规则two rules to remember

理解 async / await，只需要牢记两条规则，其他结论都能从它们推导出来。

规则一：async 函数总是返回 Promise

return 一个普通值，会被自动包装成一个「已兑现」的 Promise； 函数内部抛出错误，会变成一个「已拒绝」的 Promise。 换句话说，调用一个 async 函数，你永远不会直接拿到值，拿到的永远是一个 Promise。

javascript demo/async-rules.js 

async function f() {
  return 1;                  // 普通值 → 自动包成已兑现的 Promise
}
f() instanceof Promise;                   // true
f().then(function (v) { console.log(v); }); // 1

async function g() {
  throw new Error('boom');   // 抛错 → 变成被拒绝的 Promise
}
g().catch(function (err) { console.log(err.message); }); // boom

规则二：await 暂停并取值，失败就在该行抛出

await 会暂停当前 async 函数的执行， 等后面的表达式（Promise）定型之后，把兑现的值取出来； 如果这个 Promise 被拒绝，就会在 await 这一行 抛出异常。正因为是「抛出」，它才能被外层的 try / catch 统一接住。

术语：协程（coroutine）

async / await 是 ES2017 引入的语法，底层的概念叫「协程」—— 也就是可恢复的函数：函数在 await 处挂起， 把控制权交还给调用方；等 Promise 定型后，再从挂起的地方继续往下执行。 这也解释了为什么调用 async 函数时拿到的是 pending 的 Promise —— 那一刻函数体还没跑完。

写法 实际发生什么
async function f() { return 1 } 返回一个已兑现的 Promise，兑现值是 1（普通值被自动包装）。
async function f() { throw err } 返回一个已拒绝的 Promise，拒绝原因就是抛出的 err。
await 1 直接得到 1。非 Promise 值也能 await，会被当成已兑现的 Promise 立刻取出。
await Promise.resolve(2) 暂停当前 async 函数，等它定型后取出 2，再从挂起处继续。
await Promise.reject(new Error('x')) 在 await 这一行抛出异常，可以被外层 try / catch 捕获。
口诀
async 总返回 Promise，await 失败即抛出，所以错误处理能回归 try/catch。
1.3

错误处理回归 try / catchunified error handling

这是 async / await 最大的实际收益：一次 try / catch 就能同时接住三种失败 —— 网络错误、非 2xx 响应、以及 res.json() 解析失败。 收尾动作统一放进 finally（例如关闭 loading）。

javascript demo/try-catch.js 

async function load(url) {
  const loading = document.querySelector('#loading');
  loading.hidden = false;

  try {
    const res = await fetch(url);
    if (!res.ok) {
      throw new Error('HTTP ' + res.status);   // 非 2xx：手动抛错
    }
    const data = await res.json();             // 解析失败也会抛错
    return data;
  } catch (err) {
    // 网络错误、非 2xx、JSON 解析失败，全都在这里被捕获
    console.error('加载失败：', err);
    return null;
  } finally {
    // 无论成功还是失败都会执行，用来收尾（关 loading）
    loading.hidden = true;
  }
}
小心
① await 一个被拒绝的 Promise 会抛出异常， 所以必须在 async 函数内用 try / catch 包住，否则就变成一个没人处理的拒绝。
② 同步调用一个 async 函数时，拿到的仍然是 pending 的 Promise （因为函数体还没执行完）。所以 console.log(load()) 打印出来是 Promise { <pending> }，而不是数据。
1.4

四个常见易错点common pitfalls

  • await 只能用在 async 函数内部（模块顶层 await 是另一个新特性，别混用）。
  • 忘记写 await：拿到的是 Promise 而不是数据，data.name 会是 undefined。
  • forEach + await 不生效：forEach 不会等待回调，循环会立刻跑完。
  • 串行 await 的代价：三个互不依赖的请求写成三个连续 await，总耗时是三者之和。

① await 只能用在 async 函数内部

javascript demo/pitfalls.js 

// ✗ 语法错误：await 不能出现在普通函数里
function bad() {
  const data = await fetch(url);   // SyntaxError
}

// ✓ 必须把所在的函数声明成 async
async function good() {
  const data = await fetch(url);
}

② 忘记写 await

javascript demo/pitfalls.js 

// ✗ 忘了 await：data 是 Promise，不是数据
async function wrong() {
  const data = fetch(url);
  console.log(data.name);   // undefined —— Promise 上没有 name
}

// ✓ 写上 await 才有真正的数据
async function right() {
  const res = await fetch(url);
  const data = await res.json();
  console.log(data.name);   // 真实的姓名
}

③ forEach + await 不生效

javascript demo/pitfalls.js 

const ids = [1, 2, 3];

// ✗ forEach 不会等待回调，循环立刻跑完，顺序无法保证
ids.forEach(async function (id) {
  const data = await fetchUser(id);
  console.log(data);
});

// ✓ 需要按顺序等待：用 for...of
for (const id of ids) {
  const data = await fetchUser(id);   // 严格按 1 → 2 → 3
  console.log(data);
}

// ✓ 需要并行：map 产生 Promise 数组，再交给 Promise.all
const all = await Promise.all(ids.map(function (id) {
  return fetchUser(id);
}));

④ 串行 await 的代价

javascript demo/pitfalls.js 

// ✗ 串行：三个互不依赖的请求，总耗时 = 三次之和
const a = await fetchUser(1);   // 约 300ms
const b = await fetchUser(2);   // 约 300ms
const c = await fetchUser(3);   // 约 300ms
// 合计约 900ms

// ✓ 并行：同时发出，总耗时 = 最慢的那一次
const [a2, b2, c2] = await Promise.all([
  fetchUser(1),
  fetchUser(2),
  fetchUser(3),
]);
// 合计约 300ms
判断
问自己一句：后一个请求需要前一个的结果吗？ 需要就串行（for…of / 连续 await），不需要就用 Promise.all 并行。 右边演示 A 可以当场量出两者耗时差多少。
1.5

Promise 还是 async / awaitwhich one to use

两者不是取代关系。课件给出了一张对比：async / await 更好读， 但在调试、传递复用、内存与老环境支持上各有取舍。

维度 Promise 链 async / await
可读性 then / catch 链式，长了会有嵌套感 像同步代码，顺序清晰，更好读
调试 调用栈相对连续 调用栈会跳来跳去，断点与单步更难受
传递与复用 Promise 对象可以随意传递、挂多个处理器 值被 await 取出后继续往下走，复用性弱一些
内存与栈回溯 链式实现保留完整栈信息，占用更多内存 相对更轻
老浏览器支持 更好（ES6 普及更早） 需要 ES2017，老环境要先转译
性能 一般 课件说在某些场景更优
结论
按具体需求、环境和目标选择，不是谁取代谁。 日常业务代码优先 async / await（好读、好写错误处理）； 需要把一个「未来的值」到处传递、给多个地方挂处理器时，直接用 Promise 更自然。
1.6

一段健壮的 async / await 封装a robust wrapper

把前面所有知识点拼起来：await fetch(url) → 判断 !res.ok 手动抛错 → await res.json() → 统一 try / catch / finally。这段代码可以直接抄进作业。

javascript demo/async-robust.js 

// 一个健壮的请求封装：把三类错误翻译成人话
async function fetchJSON(url, options) {
  let res;
  try {
    res = await fetch(url, options);
  } catch (err) {
    throw new Error('网络错误：' + err.message);   // 断网 / DNS / CORS
  }

  if (!res.ok) {
    throw new Error('HTTP ' + res.status + ' ' + res.statusText); // 4xx / 5xx
  }

  const type = res.headers.get('content-type') || '';
  if (!type.includes('application/json')) {
    throw new Error('响应不是 JSON：' + type);
  }

  try {
    return await res.json();                        // 解析失败也会抛
  } catch (err) {
    throw new Error('JSON 解析失败：' + err.message);
  }
}

// 使用：错误统一回到 try / catch，收尾统一放 finally
async function main() {
  showLoading(true);
  try {
    const user = await fetchJSON(API + '/users/1');
    render(user);
  } catch (err) {
    showError(err.message);
  } finally {
    showLoading(false);
  }
}
规律
所有「可能失败」的动作都抛出去，只在最外层 try / catch 收一次；finally 只负责收尾。 这样错误处理只有一个入口，不会散在各处。

这一节要带走的三句话takeaways

01

async 总是返回 Promise

return 普通值会被自动包装成已兑现的 Promise；函数内抛错会变成被拒绝的 Promise。

02

await 失败即抛出，所以能 try / catch

await 被拒绝的 Promise 会在那一行抛异常，错误处理因此回归同步风格的 try / catch / finally。

串行 await 是三者之和

互不依赖的请求写成连续 await 会累加耗时；用 Promise.all 并行，总耗时约等于最慢的那一个。
