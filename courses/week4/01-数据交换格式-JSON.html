知识点 01 · 对应课件 3.1 Data Interchange

数据在传出去之前，先变成字符串

前面几周页面里的内容都是写死在 HTML 里的。一旦内容要来自服务器， 第一个问题就出现了：两种不同的语言、不同的系统之间，靠什么格式交换数据？ 这一节先把这件事说清楚，再落到前端最常用的两个方法 JSON.stringify 与 JSON.parse。

必考 JSON / YAML / XML stringify / parse localStorage
1.1

为什么需要「数据交换格式」standard interfaces

想象你要把一段 C 程序算出来的结果交给一个 JavaScript 程序用。 C 有结构体，JS 有对象，Python 有字典 —— 三套内存模型互不认识。 所以软件世界里需要一种标准接口：一个双方都认的中间格式。

物理世界

插座 / USB

插头和插座的形状被事先约定好，所以任何厂家都能互通。

数据世界

数据交换格式

一种极简的「标记语言」，内容只是数组、对象、数字、字符串、布尔值的组合。

关键动作

结构化 → 字符串

先序列化成纯文本才能传输，接收方再反序列化回自己的数据结构。

一句话
数据交换格式的本质，是把「结构化数据」变成「可以传输的字符串」。 传输通道（网线、HTTP）只能搬字节，搬不了内存里的对象。
1.2

JSON / YAML / XML 三者的取舍pick your format

下面用同一份数据（三个地点的 suburb 与 postcode）写出三种格式，横向对比一下就能看出差别。

json locations.json 
{
  "locations": [
    { "suburb": "Kensington", "postcode": 2033 },
    { "suburb": "Mascot",     "postcode": 2020 },
    { "suburb": "Sydney CBD", "postcode": 2000 }
  ]
}
yaml locations.yaml 
---
locations:
- suburb: Kensington
  postcode: 2033
- suburb: Mascot
  postcode: 2020
- suburb: Sydney CBD
  postcode: 2000
xml locations.xml 
<?xml version="1.0" encoding="UTF-8"?>
<root>
  <locations>
    <element>
      <postcode>2033</postcode>
      <suburb>Kensington</suburb>
    </element>
    <element>
      <postcode>2020</postcode>
      <suburb>Mascot</suburb>
    </element>
  </locations>
</root>
格式 可读性 体积 解析成本 典型用途
JSON 不错 小 低（原生支持） 前后端 API 通信，事实标准
YAML 最好（可以写注释） 小 中（需第三方库） 各种配置文件（CI、K8s、docker-compose）
XML 差（开闭标签太吵） 大 高 遗留系统、RSS、部分企业接口

XML 的三个现实问题

  • 更啰嗦：同样的数据，开闭标签让一句话要读好几遍。
  • 更费力：解析器要处理属性、命名空间、DTD，理解和实现成本都更高。
  • 更多字节：同样的信息占用更多带宽，移动网络下代价明显。
取舍
选格式看场景，不是看新旧。 前后端通信选 JSON，因为体积小、解析快、和 JS 最亲近； 写配置选 YAML，因为能写注释、可读性最好； 对接老旧系统时你依然会遇到 XML —— 不是因为它好，而是因为它已经在那里了。
1.3

JSON 不等于 JS 对象字面量four syntax limits

这是最容易在考试里丢分的一点：JSON 的语法是 JavaScript 对象字面量的一个严格子集。 JS 里能写的东西，JSON 里不一定能写。

✗ 这一段是合法的 JS，但不是合法 JSON
const bad = {
  name: 'Bob',        // key 没加引号
  age: 23,            // 尾逗号
  // 这里有一行注释
  nickname: undefined,
  greet: () => 'hi',
};
✓ 同一份数据，合法的 JSON
{
  "name": "Bob",
  "age": 23
}

四条必须记住的限制

  • key 必须是双引号字符串："name" 可以，name 和 'name' 都不行。
  • 不能有尾逗号：最后一个成员后面不能多一个逗号。
  • 不能写注释：JSON 没有任何注释语法（这也是 YAML 在配置文件里更受欢迎的原因）。
  • 不支持 undefined、函数、NaN：这些值在序列化时会被丢掉或被强制转换。
陷阱
因为JSON.parse 遇到语法错误会直接抛异常， 所以任何来自外部的 JSON 字符串都要放进 try / catch。 右边演示台的第 3 个按钮专门演示这件事。
1.4

前端最常用的两个方法stringify & parse

javascript 01-json-basics.js 
const DATA = {
  names: [
    { first: 'Bob',   last: 'Carr' },
    { first: 'Julia', last: 'Gillard' },
  ],
};

// ① 对象 → 字符串（序列化）
const text = JSON.stringify(DATA);
console.log(typeof text);        // "string"  ← 不是对象！
console.log(text);
// {"names":[{"first":"Bob","last":"Carr"},{"first":"Julia","last":"Gillard"}]}

// ② 加缩进只为好看，服务器收到的还是同一份数据
const pretty = JSON.stringify(DATA, null, 2);

// ③ 字符串 → 对象（反序列化）
const back = JSON.parse(text);
console.log(back.names[0].first); // "Bob"

两个参数要注意

  • 缩进参数只影响外观：JSON.stringify(v, null, 2) 里的 2 只是加换行和空格，方便人看；体积反而变大，所以不要拿它当传输格式。
  • 无法序列化的值会被处理掉：值为 undefined 或函数的键会整个消失， NaN / Infinity 会变成 null， Date 会变成 ISO 字符串。右边演示台可以直接看到结果。
补充
JSON.stringify 遇到循环引用（对象的属性指回自己）会抛 TypeError: Converting circular structure to JSON。 这在遍历 DOM 节点或父子上级互相引用时很常见。
1.5

为什么 JSON 总和 localStorage 一起出现persist to disk

localStorage 是浏览器给的一个键值存储，关闭标签页、重启浏览器后数据还在。 但它有一个硬限制：只能存字符串。

javascript 01-localstorage.js 
const KEY = 'w4:members';

// ✗ 直接存对象：浏览器会先调用 String(obj)
localStorage.setItem(KEY, { name: 'Bob' });
localStorage.getItem(KEY);   // "[object Object]" —— 数据已经丢了

// ✓ 正确做法：对象 → 字符串 → 存
const members = [{ name: 'Bob' }, { name: 'Julia' }];
localStorage.setItem(KEY, JSON.stringify(members));

// ✓ 读出来必须 parse 回对象
const raw = localStorage.getItem(KEY);      // 字符串
const list = raw ? JSON.parse(raw) : [];     // 对象数组
console.log(list[0].name);                   // "Bob"

// ✓ 因为 parse 可能抛错，生产代码要包一层
function loadMembers() {
  try {
    return JSON.parse(localStorage.getItem(KEY)) ?? [];
  } catch (err) {
    console.warn('本地数据损坏，已重置：', err);
    localStorage.removeItem(KEY);
    return [];
  }
}
规律
凡是「只能存文本」的介质（localStorage、cookie、URL query、请求体）， 都遵循同一套动作：写之前 stringify，读之后 parse。 记住这个规律，后面几节的 HTTP 请求体会反复用到。
1.6

这一节要带走的三句话takeaways

01

JSON 是字符串，不是对象

看到双引号包住整个结构，它就是一个 string；能用 .key 取值才是对象。

02

key 必须双引号、不能有尾逗号、不能写注释

这四条限制决定了「JS 里能跑」不等于「JSON 能解析」。

03

写前 stringify，读后 parse

所有只能存文本的介质都遵循这一条，且 parse 一定要包 try/catch。
