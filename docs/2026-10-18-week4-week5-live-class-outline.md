## 3. Part 1 · Week 4：异步与网络（40 分钟，8 节）

### 1.1 数据交换 Data Interchange（4'）

- **课件**：`3.1-data-interchange.pdf`
- **要点**
  - 前后端为什么必须交换数据：页面内容大多**不是写死在 HTML 里**，而是请求回来的。
  - 数据交换格式的本质：把「结构化数据」变成**可以传输的字符串**。
  - JSON / YAML / XML 的取舍：JSON 体积小、解析快、与 JS 最亲近；YAML 好读、常用于配置；XML 冗长、历史包袱重。
  - **JSON ≠ JS 对象字面量**：key 必须用双引号、不能有尾逗号、不能写注释、不能是 `undefined`。
- **课堂小题（题库 JS-Q1）**
  > JSON、YAML、XML 都可以表示结构化数据，三者的典型取舍是什么？JSON 相比 JavaScript 对象字面量在语法上有哪些限制？
  **参考要点**：JSON 小/快/生态好；YAML 可读性最好、多用于配置；XML 啰嗦、多用于遗留系统。JSON 限制：key 必须双引号、无尾逗号、无注释、不支持 `undefined`/函数。
- **讲授提示**：现场写一个 JS 对象 → `JSON.stringify` 对比屏幕，让学生看到 key 被加上了引号。一句话记住：**JSON 是字符串，不是对象。**

### 1.2 客户端-服务器模型与 AJAX Intro（5'）

- **课件**：`ajax-intro.pdf`
- **要点**
  - 一次「请求-响应循环」：客户端发起请求并展示界面，服务器处理业务与数据存取后返回响应。
  - **客户端不持有权威数据**，服务器才是数据的唯一权威来源。
  - **延迟 vs 吞吐**：客户端盯「单次快不快」（latency），服务器盯「单位时间能扛多少」（throughput）。
  - **AJAX 不是某项具体技术**，而是一组「不整页刷新即可局部更新」的技术集合。
  - 全称拆解：**Asynchronous**（不阻塞页面）/ **JavaScript**（发起语言）/ **XML**（早期数据格式，今天基本被 JSON 取代）。
- **课堂小题（题库 JS-Q5）**
  > AJAX 是一门具体技术吗？它的全称分别代表什么含义？
  **参考要点**：不是，是技术集合；异步不阻塞、用 JS 发起、XML 已被 JSON 取代；实现上依赖 XHR 或 fetch。
- **讲授提示**：用「刷微博不整页刷新」的例子讲为什么需要 AJAX，比讲定义有效。

### 1.3 异步模型与事件循环（7'，★ 本段最重）

- **课件**：`javascript-async-callbacks.pdf`
- **要点**
  - **同步 vs 异步**：异步≠快，而是「不等待、先往下走」。
  - **抢占式 vs 协作式多任务**：操作系统是抢占式（可被强制打断）；**JS 是协作式**（只有当前任务主动结束，才轮到下一个）。
  - **事件循环四步**：① 执行调用栈中的同步代码 → ② 清空微任务队列 → ③ 必要时渲染 → ④ 取下一个宏任务，回到 ①。
  - **后果**：一个长时间运行的 handler 会把后续任务**和页面渲染**全部堵死 → 用户看到「卡死」。
- **课堂小题（题库 JS-Q7）**
  > 请按顺序说明事件循环的四个步骤，并解释为什么一个长时间运行的 handler 会让页面卡死。
  **参考要点**：四步如上；因为 JS 是协作式单线程，当前 handler 不返回，事件循环就无法推进，队列中的任务与渲染一起被阻塞。
- **板书建议**：白板上画「调用栈 / 微任务队列 / 宏任务队列 / 渲染」四栏，现场推一遍 `setTimeout`。

### 1.4 回调与「回调地狱」（4'）

- **课件**：`javascript-async-callbacks.pdf`
- **要点**
  - 回调的本质：把「未来才会发生的事」交给一个函数去处理。
  - 问题**不在回调本身**，而在流程一复杂就层层嵌套，导致：可读性差、错误处理分散、违背 DRY / SRP。
  - 这是理解 Promise 和 async/await 的铺垫——它们解决的是**写法**，不是「回调不能用」。
- **课堂小题（板书题，现场口答）**
  > 下面代码的输出顺序是什么？为什么？

  ```js
  console.log('A')
  setTimeout(() => console.log('B'), 0)
  console.log('C')
  ```
  **参考要点**：`A → C → B`。`setTimeout` 的回调进入**宏任务队列**，必须等调用栈清空（同步代码跑完）后才执行，哪怕延迟写的是 0。
- **讲授提示**：这题去年翻车率很高，一定要讲透「延迟 0 也不等于立刻执行」。

### 1.5 XMLHttpRequest（4'）

- **课件**：`ajax-xhr.pdf`
- **要点**
  - 定位：浏览器**早期**发起异步请求的方式；今天少用，但机制是理解异步请求的基础。
  - `onload` / `onerror` 的分工：**只有网络层失败**（连不上、被中断）才走 `onerror`。
  - **4xx / 5xx 不算 error**：服务器已经回了响应，只是业务失败，必须自己查 `status`。
  - 状态码：`200` 成功 / `4xx` 客户端错误（404 资源不存在、400 参数错）/ `5xx` 服务端错误。
- **课堂小题（题库 JS-Q8）**
  > 使用 XMLHttpRequest 时，哪些情况会进入 error 回调，哪些情况要靠 status 判断？200 / 4xx / 5xx 分别是什么含义？
  **参考要点**：仅网络层失败进 error；4xx/5xx 属于「收到响应」，走 status 分支。
- **讲授提示**：这条规则完全适用于后面的 fetch（`fetch` 遇到 404 也不会 reject），在这里埋下伏笔。

### 1.6 Promise 与 fetch（7'，★ 本节最重）

- **课件**：`ajax-fetch.pdf`
- **要点**
  - **四种状态**：`pending` / `fulfilled` / `rejected`，以及二者的统称 `settled`（已定型）。
  - 状态一旦从 pending 变走就**不可再变**，这是「链式」能成立的前提。
  - `.then`（处理成功，返回新 Promise 以支持链式）/ `.catch`（捕获拒绝）/ `.finally`（无论成败都执行，用于清理）。
  - 六种编排工具：`all`（全成功）/ `race`（最先定型）/ `allSettled`（全部有结果）/ `any`（最先成功）等。
  - `unhandledrejection`：没被 catch 的拒绝会冒到全局。
  - **fetch 的行为**：返回 Promise；**只在网络失败时 reject**，404/500 依然走 then，要自己判 `res.ok`。
- **课堂小题（题库 JS-Q9）**
  > Promise 有哪几种状态？`.then` / `.catch` / `.finally` 各自的分工是什么？
  **参考要点**：pending / fulfilled / rejected（+ settled 统称）；then 处理成功并返回新 Promise、catch 捕拒绝、finally 收尾清理；状态不可逆。
- **讲授提示**：现场演示一次 `fetch('/不存在的地址')` 不报错、只返回 `res.ok === false`，学生的表情就是记忆点。

### 1.7 async / await（5'）

- **课件**：`javascript-async-await.pdf`
- **要点**
  - ES2017 引入，**本质是 Promise 的语法糖**。
  - **两条核心规则**：① `async` 函数**总是返回 Promise**（return 普通值会被自动包装；抛错会变成拒绝）；② `await` 暂停当前 async 函数，等 Promise 定型后取值，**若被拒绝就在该行抛出**。
  - 因为「被拒绝就会抛出」，错误处理才能**回归 `try/catch`**——这是它最大的收益。
  - 取舍：async/await 可读性更好，但**并没有把异步变成同步**，只是写起来像同步。
- **课堂小题（题库 JS-Q10）**
  > `async` 函数的返回值有什么特性？`await` 做了什么？为什么用 async/await 后错误处理可以回归 try/catch？
  **参考要点**：async 总是返回 Promise；await 暂停并取值、拒绝则抛；所以 try/catch 能统一捕获。
- **讲授提示**：同一段请求逻辑，先写 Promise 链、再写 async/await 对照，学生自己就能说出「好在哪」。

### 1.8 HTTP Server（4'）

- **课件**：`4.2-http-server.pdf`
- **要点**
  - **Network / Internet / WWW 的层级**：Web 跑在 Internet 上，Internet 由无数 Network 组成——**Web ≠ Internet**。
  - 为什么需要协议：通信必须有「结构」双方才能互相理解；**HTTP = Hypertext Transfer Protocol**，是浏览器访问 URL 时用的主协议。
  - Express 最小服务器：`app.get('/apple', (req, res) => ...)`；**`req.query` 取 URL 参数，`req.body` 取请求体**。
  - **RESTful 与 CRUD 的映射**：POST=Create / GET=Read / PUT=Update / DELETE=Delete。
- **课堂小题（题库 NODE-Q3）**
  > RESTful API 中四种 HTTP 方法分别对应 CRUD 的哪个操作？这样设计的意义是什么？
  **参考要点**：POST→Create、GET→Read、PUT→Update、DELETE→Delete；用方法本身表达请求性质，同一 endpoint 即可表达增删改查。
- **讲授提示**：这节最容易「听过就忘」，只抓两件事：**方法=性质**、**query 与 body 的区别**。

## 5. Part 2 · Week 5：React（30 分钟，7 节）

### 2.1 命令式 vs 声明式：为什么需要 React（5'）

- **课件**：`ReactJS Introduction` + `Lifecycle` p.1–31
- **要点**
  - **命令式**：指定「怎么做」→ `document.body.style.backgroundColor = 'green'`。
  - **声明式**：只描述「结果长什么样」→ `return <body style={{ backgroundColor: 'green' }} />`，过程交给 React。
  - **为什么值得**：状态转换数量会组合爆炸——**3 个状态 = 6 种转换，50 个页面最少 2450 种转换**。命令式要逐一处理，声明式只需描述这 50 个状态。
  - 命令式的边界：简单场景很方便；**一旦 DOM 之外还有数据**（比如服务器返回的数组），就要同时维护 JS 和 DOM 两个状态机，边界情况无穷。
- **课堂小题（题库 REACT-Q1）**
  > 下面 A、B 两种写法，哪一种属于声明式？为什么 React 更推崇声明式？

  ```js
  // A
  document.body.style.backgroundColor = 'green'
  ```
  ```jsx
  // B
  return <body style={{ backgroundColor: 'green' }} />
  ```
  **参考要点**：B 是声明式；A 关注过程、B 只描述结果；声明式的价值在于状态转换的组合爆炸被框架接管。
- **讲授提示**：务必说清楚「**声明式代码不一定更少**，但扩展性和可维护性好得多」，这是常考的反直觉点。

### 2.2 JSX 语法（4'）

- **课件**：`ReactJS Introduction` p.9–13
- **要点**
  - JSX = JavaScript 的**语法扩展**，本质还是 JS，所以能存进变量、能配三元、能用 `{}` 插值。
  - `class` → **`className`**。
  - **单一根节点**：多个并列元素必须用父元素或 `<>...</>` 包起来。
  - `{}` 内**只能放表达式，不能放语句**（不能写 `if`，但可以写三元）。
- **课堂小题（题库 REACT-Q2）**
  > 下面这段 JSX 至少存在两个问题，请指出并给出改正后的写法。

  ```jsx
  const el = (
    <div class="card">Hello</div>
    <span>!</span>
  )
  ```
  **参考要点**：① `class` 应为 `className`；② 有两个并列根节点，需用 `<div>` 或 `<>` 包裹。
- **讲授提示**：改错题是这类知识点的标准考法，把「两个坑」念出来让学生记住。

### 2.3 项目结构与挂载（4'，⚠️ 需订正）

- **课件**：`ReactJS Introduction` p.5–8, 17–20
- **要点**
  - 入口 HTML 里有一个**挂载容器**（`<div id="root">`），入口 JS/TS 负责把根组件**挂载**到它上面。
  - **React 19 的写法**：`createRoot(document.getElementById('root')!).render(<App />)`。
  - HMR：保存即刷新。
  - **订正清单（必讲）**：`npx create-react-app` → 现代用 **Vite**；`ReactDOM.render(<App/>, el)` → **React 18+ 已废弃**，改 `createRoot(...).render(...)`；`.js` → `.tsx` / `.ts`。
- **课堂小题（题库 REACT-Q3）**
  > 在 React 19 项目中，入口文件应该怎样把根组件挂载到 `#root`？请说明用到的 API 与参数含义。
  **参考要点**：从 `react-dom/client` 导入 `createRoot`；`createRoot(容器).render(<App />)`；容器是真实 DOM 节点。
- **讲授提示**：明确告诉学生「slides 是旧版，考试按 React 19 答」，避免照着旧 slides 背错。

### 2.4 React 中的样式：inline style 与 className（4'）

- **课件**：`Basic "Global CSS" Usage` p.4–10
- **要点**
  - **inline style 接收的是对象**，所以是「双花括号」：外层 `{}` 是表达式，内层 `{}` 是对象。
  - 属性名必须 **camelCase**：`font-size` → `fontSize`。
  - **CSS class 路线**：`className="App"` + `import './App.css'`。
  - 两种可以**组合**使用（外层用 className，内层用 inline style）。
- **课堂小题（题库 REACT-Q4）**
  > 下面 A、B 两种写法哪种正确？另一种错在哪里？

  ```jsx
  // A
  <div style="color: red; font-size: 12px">Hi</div>
  ```
  ```jsx
  // B
  <div style={{ color: 'red', fontSize: '12px' }}>Hi</div>
  ```
  **参考要点**：B 正确；A 写成了字符串且用了 kebab-case，在 React 中不生效。
- **讲授提示**：这题几乎必考，属于「送分题」，一定要拿到。

### 2.5 CSS 作用域陷阱与隔离（3'）

- **课件**：`Basic "Global CSS" Usage` p.11–13
- **要点**
  - 核心陷阱：在某个文件里 `import './App.css'` **不代表**这些 class 只属于该文件。
  - 只要这份 CSS **被任何地方 import 过**，它的所有 class 就进入**全局作用域**，A 组件的样式会意外影响 B 组件 → **全局污染**。
  - ES module 的 `import` **不会**给 CSS 带来隔离作用域（这是最常被误解的点）。
  - 解决方向：**CSS Modules**、**CSS-in-JS**。
- **课堂小题（题库 REACT-Q5）**
  > 同学在 `A.tsx` 里写了 `import './A.css'`，以为只有 A 能用这些类，结果 B 也受影响。为什么？怎么解决？
  **参考要点**：import 只负责「引入」，不负责「限定作用域」；一旦被引入就是全局的；用 CSS Modules / CSS-in-JS 隔离。
- **讲授提示**：一句话总结：**import 管的是「有没有加载」，不是「谁能用」。**

### 2.6 虚拟 DOM 与 Diff（6'，★ 本模块最重）

- **课件**：`Lifecycle` p.32–43
- **要点**
  - **朴素方案**：任何变化都把整个 DOM 删掉重建——逻辑上正确（不必考虑状态转换），但**开销过大**。
  - **为什么 DOM 更新昂贵**：频繁改动会触发**大量 layout 重算**；而在更新阶段其实**并不关心布局**，本可以交给浏览器最后统一算。
  - **虚拟 DOM 四步**：① 在 JS 内存里保留一份 HTML 层级**副本** → ② 在副本上改动（避开真实 layout 开销）→ ③ 对新旧两棵树做 **Diff** → ④ 只把差异**外科式**地更新到真实 DOM。
  - **两个必须纠正的误解**：虚拟 DOM **没有让 DOM 变快**，它只是**减少不必要的 DOM 操作**；它也**不是浏览器的能力**，而是框架自建的一层抽象。
- **课堂小题（题库 REACT-Q6）**
  > 解释虚拟 DOM 与 Diff 如何减少真实 DOM 的更新开销。为什么不能说虚拟 DOM 让 DOM 本身变快了？
  **参考要点**：四步流程；真实 DOM 频繁改动触发 layout reflow 才是慢的根源；虚拟 DOM 只是减少无谓操作，且属于框架层抽象。
- **讲授提示**：白板画「旧树 / 新树 / 差异」三格图，比讲概念有效十倍。

### 2.7 useState 与渲染循环（4'）

- **课件**：`Lifecycle` p.44–48 + `useState hook` 视频
- **要点**
  - 语法：`const [count, setCount] = useState(0)`。
  - **state 更新是异步的**：`setCount(count + 1)` 不会立刻改变 `count` 变量，紧接着的下一行读到的是旧值。
  - 更新完成后，React 会**重新执行 render** 并把新值传进去 → 界面随之变化。
  - 完整闭环：**render → 改 state → 再 render**。
  - state **必须通过 setter 修改**，直接给变量赋值不会触发重渲染。
  - 条件渲染：`{dropdownVisible && <ul>…</ul>}`。
- **课堂小题（题库 REACT-Q7）**
  > `const [count, setCount] = useState(0)`，点击一次执行 `setCount(count + 1)`。为什么说 state 更新是异步的？更新后页面为什么会变化？
  **参考要点**：更新被排队异步处理；完成后触发 re-render 并传入新值；闭环 render→改 state→再 render。
- **讲授提示**：现场演示「连续调用两次 `setCount(count + 1)` 只加 1」，学生会立刻记住「异步」的含义。

## 6. Part 3 · Week 5：UI/UX（30 分钟，7 节）

> 这一段的特点是**没有代码**，全是判断与概念。讲法建议：**先给结论（一句话口诀），再用例子对比，最后上小题。**

### 3.1 UI 与 UX 的区别（3'）

- **课件**：`UI Fundamentals` p.2–3
- **要点**
  - **UX** = 可用性（usability）、操作流程是否合乎逻辑、用户研究（访谈 / 测试）。
  - **UI** = 图形与文案、颜色 / 像素 / 阴影等视觉设计、品牌（branding）。
  - **UI 的终极目标仍然是「让 app 更好用」**，拆成三个子目标：① 让用户**不害怕**（图形基础）② 让用户**容易找到东西**（视觉层级）③ 让用户**容易做事**（示能）。
- **课堂小题（题库 UIUX-Q1）**
  > 研究操作流程是否合乎逻辑、做用户访谈与测试，更偏 UX 还是 UI？设计按钮颜色、阴影与品牌视觉，又偏哪一个？
  **参考要点**：前者 UX（可用性与用户研究），后者 UI（视觉与品牌）；但 UI 的最终目标依然是可用。
- **讲授提示**：一句话口诀：**UX 管「合不合理」，UI 管「看不看得清」。**

### 3.2 对齐与网格系统（4'）

- **课件**：`UI Fundamentals` p.5–12
- **要点**
  - 人眼对**对齐和一致的模式**有天生的偏好 → 对齐是成本最低、收益最高的整洁手段。
  - **网格（grid）** 是达成对齐的手段。
  - **三个必背数字**：内容区 **1200px** 上限（控制每行文本长度、保证可读性）、**12 列**网格、列间 gutter **16px**。
  - **为什么是 12 列**：12 能被 **1 / 2 / 3 / 4 / 6** 整除，拆两栏、三栏、四栏、六栏都行；10 只能被 1 / 2 / 5 整除，能力弱得多。
  - 内容对齐到**列边缘**，而**不是**进入 margin。
- **课堂小题（题库 UIUX-Q2）**
  > 内容区上限 1200px、12 列网格、gutter 16px。为什么列数选 12 而不是 10？
  **参考要点**：12 的因数多（1/2/3/4/6），拆分布局更灵活；1200px 是为了可读性。
- **讲授提示**：数字题最容易考，把 1200 / 12 / 16 三个数字写在白板上别擦。

### 3.3 字体与和谐配色（4'）

- **课件**：`UI Fundamentals` p.5, 13–18
- **要点**
  - **字体：less is more**。一个项目**最多 2 个 font family**（一个标题/展示体 + 一个正文），超了就灾难。层级优先靠**同一个字体变字号 / 字重**，而不是换字体；事先用 **type scale** 定好字号阶梯。
  - **配色：受限的调色板才换得来统一感（cohesion）**——一个主色相 + 若干明暗变体 + 一个辅色 + 灰阶。
  - **和谐配色的核心判据：色相（HUE）相同，只变亮度/饱和度。** 色相一变就杂乱、分散注意力。
  - 判断是否同色相用 **HSL 比 RGB 直观**，因为 HSL 把色相单独拆了出来。
- **课堂小题（题库 UIUX-Q4）**
  > 下面两组 HSL 颜色，哪一组更可能构成和谐配色？为什么？
  > A：`(199,86,51)`、`(199,100,35)`、`(199,86,90)`
  > B：`(277,96,47)`、`(230,100,89)`
  **参考要点**：A 更和谐——A 组的 H 都是 199（同色相、只变明度饱和度）；B 组的 H 是 277 和 230，色相不同。
- **讲授提示**：口诀：**「和谐看色相，明暗随你变。」**

### 3.4 视觉层级六要素（5'）

- **课件**：`UI Fundamentals` p.19–22
- **要点**：视觉层级解决的问题是「**让最重要的最突出，让次要的安静下来**」。六个手段：
  1. **Size** 越大越重要
  2. **Color** 越亮/越饱和越重要
  3. **Contrast** 与周围差异越大越吸睛
  4. **Spacing** 留白越多越像「被请上台」
  5. **Alignment** 反直觉：**在整齐布局里唯一不对齐的那个最吸睛**
  6. **Repetition** 重复会被归入同一层级——既能「提升」一致性，也能**「降级」次要信息让用户自然忽略**
- **课堂小题（题库 UIUX-Q5）**
  > 想让界面里「限时优惠」这句最突出，可以动用视觉层级的哪些手段？至少说出 4 个。
  **参考要点**：Size / Color / Contrast / Spacing / Alignment（不对齐）/ Repetition（反向降级其他元素）。
- **讲授提示**：拿一张电商详情页截图现场分析「哪个元素被强调、用了哪几招」——这是标准考法。

### 3.5 示能性 Affordance（4'）

- **课件**：`UI Fundamentals` p.23–25
- **要点**
  - **定义**：元素的**视觉属性**让用户知道「我可以拿它做某事」；门把手、按钮都是经典例子。决定 UI 第三层目标——**让用户会做事**。
  - **三种类型（核心考点）**：
    - **Explicit 显式**：明确写出来，如按钮上写 "Click here"、箭头 `→`
    - **Pattern 模式**：靠约定俗成，如蓝色下划线 = 链接、≡ = 菜单、放大镜 = 搜索
    - **False 虚假**：看起来能点、实际不能 → **必须避免**，最容易制造困惑
  - **必须区分的相邻概念**：示能是交互**前**的提示（「我猜它能点」），**反馈（feedback）**是交互**后**的响应（「我点了，它变了」）。
- **课堂小题（题库 UIUX-Q6）**
  > 简述示能性的三种类型，并说明哪一种必须尽量避免，为什么。
  **参考要点**：Explicit / Pattern / False；False 必须避免，因为它误导用户、造成困惑；别与反馈混淆。
- **讲授提示**：现场找一找课件截图里的 false affordance（看着像按钮的装饰块），比讲定义有效。

### 3.6 UI 设计检查清单 12 条（8'，★ 本模块最重）

- **课件**：`Good & Bad UI 1` p.9–23
- **要点（12 条速览）**

| # | 原则 | 一句话 |
|---|---|---|
| 1 | 可见性 Visibility | 控件看得见吗？**识别优于回忆** |
| 2 | 示能 Affordance | 每个按钮的作用清楚吗？ |
| 3 | 反馈 Feedback | 操作后怎么知道成功了？**超过 1.5s 要 loading** |
| 4 | 一致性 Consistency | 各页面是否一致？最多 2 个字体 |
| 5 | 约束 Constraints | 是否**事前**限制了用户犯错？如空输入禁用提交 |
| 6 | 有效性与实用性 Effectiveness & Utility | 用户到底能不能完成这件事？ |
| 7 | 效率 Efficiency | 步骤能否更少？多步骤要显示进度 |
| 8 | 安全性 Safety | **事后**能不能从错误中恢复？可撤销，否则给警告 |
| 9 | 可学习性 Learnability | 是否直观？有 placeholder / 说明吗？ |
| 10 | 通用标准与惯例 Standards & Conventions | 界面是否眼熟？logo 回首页、profile 在右上 |
| 11 | 兼顾所有人 Catering to All | 新手有支持、专家不被拖慢？ |
| 12 | 美学与极简 Aesthetics & Minimalism | 只留必要信息？ |

- **两组最容易混的对比（考点）**
  - **Constraints vs Safety**：约束是**事前**限制（防错），安全是**事后**保护（能恢复）。
  - **Effectiveness vs Efficiency**：能不能**做到** vs 是否**省步骤**。
- **课堂小题（题库 UIUX-Q7）**
  > 某表单的提交按钮在输入框为空时依然可以点击，点击后页面没有任何变化。这至少违反了 12 条清单中的哪几条？
  **参考要点**：约束（空输入应禁用提交）、反馈（操作后要有成功/失败提示）、可见性（用户不知道当前状态与下一步）、一致性。
  **追问（题库 UIUX-Q8）**：空输入禁用提交 vs 删除操作提供撤销，分别对应哪两条？为什么容易混？—— 分别对应**约束**与**安全性**，一个事前一个事后。
- **讲授提示**：这一段不要按顺序念 12 条，**分组讲**：先讲「看得见 / 猜得到」（1、2、10），再讲「操作有回音」（3、5、8），最后讲「好用与克制」（6、7、9、11、12）。

### 3.7 UI 进阶概念（2'，了解即可）

- **课件**：`Good & Bad UI 1` p.24–30
- **要点**（slides 只提名、未展开，属于**名词附录**）
  - **Dark Mode**：独立设计的第二套深色配色，不是简单反色；深色下阴影几乎不可见，层级靠更亮的背景块。
  - **Microinteractions 微交互**：围绕单一任务的小反馈（点赞心形弹跳），呼应「反馈」原则。
  - **Designing for Emotions 情感化设计**：插画、文案语气、空状态，让产品有「性格」。
  - **Cognitive Load 认知负荷**：识别优于回忆、减少选项、分步引导、遵循惯例，都是为了减负。
- **课堂小题（题库 UIUX-Q9）**
  > 为什么说「降低认知负荷」与「限制配色、字体数量」的目标是相同的？
  **参考要点**：配色/字体失控 → 用户要反复辨认它们是否代表不同含义，白白消耗注意力；受限调色板 + 最多 2 个字体建立统一感，把注意力留给真正重要的内容。
- **讲授提示**：明确说「**这四条了解即可**，别在这上面花时间，先把对齐 / 层级 / 示能 / 一致性打牢」。

## 7. Part 4 · 收尾（10 分钟）

### 7.1 三条必背清单（每题都在考它们）

```
① 事件循环四步
   执行同步代码 → 清空微任务 → 必要时渲染 → 取下一个宏任务

② 虚拟 DOM 四步
   内存副本 → 在副本上改动 → Diff 新旧树 → 外科式更新真实 DOM

③ UI 12 条清单
   可见性 / 示能 / 反馈 / 一致性 / 约束 / 有效性 / 效率
   / 安全性 / 可学习性 / 惯例 / 兼顾所有人 / 极简
```

### 7.2 两句话收尾

- **Week 4 回答的是「数据怎么从服务器来」**：客户端-服务器 → 异步模型 → 回调 → Promise → async/await → HTTP Server。
- **Week 5 回答的是「数据怎么变成用户能顺下去的界面」**：React 用声明式接管 DOM 更新，UI/UX 用对齐 / 层级 / 示能 / 反馈让人不迷路。

### 7.3 课后作业建议

- 全量练：题库 `week-4`（14 题）+ `week-5`（16 题），共 30 题。
