# Week 4 本周导览 PPT 化改造设计

## 背景

当前 `week-4/overview` 只有 2 张 slide：

1. 一张封面页
2. 一张通过 iframe 嵌入 `public/course-demos/week4/index.html` 的演示页

这导致“本周导览”虽然被放进了 SlideDeck，但内容组织仍然继承了原始长网页的滚动逻辑，不符合课程模块当前希望采用的 `PPT 式逐页讲授` 体验。导览页承担的是“建立认知地图”的职责，不应该继续依赖完整可滚动网页。

## 目标

把 `week-4/overview` 从“2 页 + iframe 长网页”改造成“4 页纯 slide 导览”，满足以下目标：

- 不再在导览页中嵌入 `week4/index.html`
- 每一页都在 Slide 舞台内完整展示，尽量不产生垂直滚动
- 导览只负责建立全局主线，不抢后续 `JSON / XHR / fetch / Promise / async-await` 五节的详细讲解内容
- 保持现有 Week 4 绿色主题、课程模块的纸张感视觉和现有 SlideDeck 交互不变

## 范围

本次只修改以下内容：

- `src/lib/content/courses.ts` 中 `week-4` 的 `overview` lesson slides 数据
- 如现有 slide 类型不足以承载导览页的版式，则补充最小必要的 slide 结构与渲染支持

本次不包含：

- 不改 `week-4` 其余五节的内容结构
- 不改原始 `public/course-demos/week4/*.html`
- 不调整 SlideDeck 顶部工具条、底部翻页条和目录交互

## 信息架构

### Page 1：封面页

角色：建立 Week 4 的总主题。

建议信息：

- 标题：`数据怎么从服务器来`
- 副标题：强调这周不是记 API，而是理解“数据回来之前前端在经历什么”
- 主线提示：`字符串 -> 发请求 -> 等结果 -> 处理异步 -> 写得更顺`

这页保留强标题，但不再只是简单罗列 5 个知识点名称。

### Page 2：主线地图页

角色：把 5 个知识点串成一条连续链路。

核心链路：

`JSON -> XHR -> fetch -> Promise -> async/await`

每个节点只回答一句话：

- `JSON`：对象怎么变成可传输字符串
- `XHR`：浏览器最早怎么发异步请求
- `fetch`：现代请求 API 怎么拿响应
- `Promise`：异步结果怎么被组织起来
- `async/await`：怎么把异步代码写得像同步流程

这页强调“它们是同一条链上的不同层次”，而不是 5 个并列孤岛。

### Page 3：知识点总览页

角色：作为导览索引，告诉用户“这一周具体会展开哪 5 节”。

版式建议：

- 采用 `2 + 3` 卡片阵列
- 每张卡信息固定，避免文字过多

每张卡回答 3 件事：

- 它讲什么
- 它解决哪一步问题
- 它会在哪一节展开演示

该页只做地图索引，不进入 API 细节，不放代码块，不嵌演示。

### Page 4：本周带走什么

角色：导览收束页。

建议放 3 条 takeaways：

1. 这一周的核心不是 API 名字，而是理解“数据从服务器回来之前，前端一直在等”
2. `fetch / Promise / async-await` 是同一条链上的不同层次，不是互相割裂的知识点
3. 学完本周后，要能从“读字符串”一路走到“发请求并处理结果”

页底增加轻量学习路径提示：

`先看总览 -> 再逐节跑演示 -> 最后回题库`

## 版式与交互原则

- 所有页面优先使用现有 SlideFrame 容器，保持和课程其他周次一致的页眉、边框、阴影与滚动约束
- 单页信息量控制在“不滚动或极少滚动”的范围内
- 导览页不再嵌 iframe，避免用户在一张导览 slide 内再次进入长网页阅读模式
- 视觉上延续 Week 4 的 emerald 主题，不引入新的主色体系
- 文案语气偏“教学引导”，而不是产品介绍或营销文案

## 实现方案

优先采用“数据驱动 + 轻量扩展”的方式：

1. 先把 `week-4/overview` 的 slide 数据从 2 页改成 4 页
2. 尽量复用现有 `cover / outline / closing` 类型
3. 如果现有 `outline` 或 `content` 无法优雅表达“主线地图页”或“5 卡片总览页”，则新增最小必要的 slide kind，并在 `SlideRenderer.tsx` 中增加对应渲染分支
4. 新增版式时遵守现有课程模块的视觉语言，不另起一套组件体系

推荐映射如下：

- `Page 1`：可沿用 `cover`
- `Page 2`：新增更适合流程链表达的 `roadmap` 或同等语义 slide
- `Page 3`：新增更适合固定卡片阵列的 `overview-grid` 或同等语义 slide
- `Page 4`：沿用 `closing`

如果实现时发现新增 slide kind 会引入过多类型扩散，则可退而求其次，把 Page 2 / Page 3 映射为 `content` 并为其补充结构化字段，但前提是渲染结果仍然足够像 PPT，而不是占位骨架。

## 验收标准

- 打开 `/courses/week-4/overview` 后，本节总页数变为 4 页
- “本节目录”中不再出现 iframe 演示页，而是 4 个纯 slide 标题
- 任一页面在常规桌面视口下都不会退化为“长网页塞进 slide”的体验
- 导览完成后，用户能明确看出 Week 4 的主线是：
  `JSON -> XHR -> fetch -> Promise -> async/await`
- Week 4 其他五节保持现状，不产生行为回归

## 风险与取舍

- 如果直接复用现有 `content` 占位页，开发成本低，但页面容易继续呈现“半成品骨架”感，不足以承担正式导览功能
- 如果为导览新增 1 到 2 种 slide 类型，成本略高，但能把“地图感”和“卡片索引感”做扎实，后续 Week 4 其他节也可能复用

综合取舍，本次推荐接受小幅度渲染层扩展，以换取更符合课程 PPT 语境的导览体验。
