# Week 4 模拟试卷卷面结构抛光设计

## 1. 目标

把当前已经补齐覆盖面的 Week 4 模拟试卷，从“按章节补齐的题目集合”整理成“更像正式模拟卷”的卷面结构。

本次抛光的重点不是继续加题，而是：

- 重排题序
- 合并重复表达的相近题
- 拉开基础题与综合题的难度梯度
- 保留 `JSON / XHR / fetch / Promise / async-await / HTTP-Express` 六条主线
- 继续遵守“试卷新增或重写的知识点，要在题库中保持同步覆盖”的原则

## 2. 当前问题

当前 Week 4 正式试卷已经覆盖 6 个主章节，但卷面仍有 3 个结构问题：

### 2.1 章节重复感偏强

前半部分已经涉及 `fetch / HTTP / Promise`，后半部分又拆出同主题题目，学生会感到“同一个知识点被问了两次，但只是换了一个说法”。

### 2.2 大题数量偏碎

目前是 `9` 道大题、`44` 分。章节覆盖是齐的，但阅读体验更像题库拼接，不像一份完整试卷。

### 2.3 难度节奏不够明显

卷面缺少“先基础、再机制、后综合”的层次推进，导致学生做题时不容易进入状态。

## 3. 选定方案

采用“六大题卷”方案，把卷面收束成 6 道大题，每道题对应 1 条课程主线：

1. JSON
2. XHR
3. fetch
4. Promise
5. async / await
6. HTTP / Express

这是最符合当前课程结构的方案。它能同时满足 3 个目标：

- 让卷子看起来像正式模拟卷
- 保持章节边界清楚
- 避免旧版 9 题结构造成的重复感

## 4. 设计原则

### 4.1 六章不丢

无论怎么重排，六个主章节必须全部保留，不允许为了“更顺”而删掉某一章。

### 4.2 优先合并，不盲目扩题

当前题目数量已经足够支撑一套完整卷面。抛光时优先合并和重排，不继续膨胀题量。

### 4.3 每道大题内部形成递进

每道大题内部的子问按下面的节奏组织：

- 第一个小问：概念辨析 / 基础判断
- 第二个小问：代码理解 / 行为解释
- 第三个小问：改写 / 取舍 / 错误处理

并非每题都必须有 3 小问，但应尽量有这种从浅到深的层次。

### 4.4 题库覆盖不退化

卷面重排后，题库中对应知识点仍必须保留。抛光不应造成“卷子更好看了，但题库练习题变少了”。

## 5. 新卷面结构

### Q1 JSON 与 localStorage

**目标：** 先用最容易进入状态的题开卷，帮助学生快速进入 Week 4 主题。

**覆盖内容：**

- JSON 与 JS 对象字面量的区别
- `JSON.stringify`
- `JSON.parse`
- localStorage 为什么总和 JSON 成对出现
- 非法 JSON 的兜底

**题型风格：**

- 概念辨析
- 简短代码理解
- 安全解析策略

### Q2 XMLHttpRequest 与 AJAX

**目标：** 让学生先理解“旧式异步请求”以及错误路径分工。

**覆盖内容：**

- AJAX 的目的
- `onload` vs `onerror`
- `status` 判断
- `responseText` 为什么还是字符串
- 为什么 404/500 不算网络错误

**题型风格：**

- 请求流程理解
- 状态分支判断
- 字符串到对象的解析

### Q3 fetch 与 Response

**目标：** 在 XHR 之后自然过渡到现代 API，让学生看清 `Response` 与 data 的两层结构。

**覆盖内容：**

- `fetch(url)` 返回 Promise
- `await fetch(...)` 拿到的是 `Response`
- `res.ok` / `res.status`
- `res.json()` 只是 body 读取步骤

**题型风格：**

- Response vs data 的区分
- 404/500 场景的处理
- 读取 body 的时机与原因

### Q4 Promise 状态与编排

**目标：** 单独讲清 Promise 本体，避免和 fetch 完全揉在一起。

**覆盖内容：**

- `pending / fulfilled / rejected / settled`
- `.then / .catch / .finally`
- 为什么链式成立
- `Promise.all` 与 `Promise.allSettled`

**题型风格：**

- 状态概念题
- 链式语义题
- 组合器取舍题

### Q5 async / await 与并行控制

**目标：** 把 Promise 的使用方式收束成更接近业务代码的写法。

**覆盖内容：**

- `async` 总返回 Promise
- `await` 成功取值、失败抛错
- `try/catch` 为什么能重新接住错误
- 连续 `await` 的问题
- `Promise.all` 并行

**题型风格：**

- 语义解释
- 改写或重构
- 性能取舍

### Q6 HTTP / Express 请求与响应

**目标：** 最后一题把客户端异步与服务端响应连起来，形成课程闭环。

**覆盖内容：**

- HTTP 是协议
- request / response 的职责
- `req.query` vs `req.body`
- `express.json()`
- `res.json(...)`

**题型风格：**

- 请求-响应模型解释
- Express 取参与输出规范
- 前后端契约统一

## 6. 分值设计

建议把整卷保持在 `40-48` 分之间，继续采用当前 `44` 分的总分，不再继续膨胀。

推荐分布：

- Q1 JSON：8 分
- Q2 XHR：8 分
- Q3 fetch：6 分
- Q4 Promise：6 分
- Q5 async / await：8 分
- Q6 HTTP / Express：8 分

这样分配的理由：

- JSON、XHR、async/await 更适合承载“基础 + 解释 + 改写”三层结构，可略重
- fetch 与 Promise 保持中段分值，避免与前后章节重复抢权重
- HTTP / Express 放在结尾，作为综合收束，分值不应太轻

## 7. 内容处理策略

### 7.1 保留有价值的现有题料

不是推翻重做，而是从现有 Week 4 卷中提取已写好的题干、子问与答案，重新归类到 6 道大题中。

### 7.2 合并重复表达

若两道题本质上都在问同一件事，例如：

- `fetch` 为什么不自动因 404 reject
- 为什么要先检查 `res.ok`

则优先合并成同一大题里的两个小问，而不是在卷子中分散重复出现。

### 7.3 保持答案口径统一

重排之后，各题的 `answerMdx` 和 `markingMdx` 要继续保持现在这套教学型口径，不突然变成另一种更短或更学术的风格。

## 8. 与题库的同步要求

本次主要是卷面结构抛光，不以新增题库题为目标；但如果抛光过程中出现以下情况，则题库必须同步：

- 某个卷面知识点被改成了新的、更准确的问法
- 某个章节的卷面重点发生偏移
- 某个原本拆开的知识点被合并后，题库需要调整映射口径

同步底线：

- Week 4 题库仍然覆盖 6 个主章节
- 不删除现有为了覆盖面而新增的题库题
- 若卷面术语更新，题库知识点命名也要同步

## 9. 验证要求

抛光后至少要验证下面这些点：

### 9.1 结构验证

- 正式 Week 4 模拟试卷收束为 6 道大题
- 题序从基础到综合更自然
- 总分与各题 marks 自洽

### 9.2 覆盖验证

- 六个主章节仍全部存在
- 题库六章覆盖不退化

### 9.3 回归验证

- mock exam 列表页正常读取 Week 4 试卷
- mock exam 详情页正常渲染重排后的题目
- 现有内容测试和 mock exam 页面测试继续通过

## 10. 非目标

本次不做以下事情：

- 不再继续扩题量
- 不重写 mock exam 页面 UI
- 不扩展到 Week 5
- 不重新设计题库 schema
- 不顺带恢复 `week4-sim` 旧卷入口

## 11. 结果预期

完成后，这套 Week 4 试卷应该具备这些特征：

- 一眼看上去就是按课程主线组织的正式模拟卷
- 题目从基础理解逐步走到综合应用
- 不再有明显的知识点重复感
- 题库与试卷仍保持一致的章节覆盖关系
