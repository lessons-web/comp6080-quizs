# Demos 模块设计

日期：2026-10-23  
范围：COMP6080 课程模块中的可运行实验统一迁移到独立 `demos` 路由体系

## 1. 背景

当前 `Week 4` 的课程内容已经在向“PPT 化”收敛：一页一个知识点，尽量不滚动，强调知识点递进与讲解节奏。

但可运行实验的形态天然不同：

- 需要输入、按钮、日志、输出区
- 往往需要更高的信息密度
- 更适合长时间停留、反复操作
- 很容易在 slide 内形成大面积滚动区域

因此把 demo 继续以内嵌 `iframe` 的形式放进课件页，会让课程页同时承担“讲解”和“实验台”两种职责，破坏课程模块的一致性。

## 2. 目标

本次设计希望建立一个独立、可复用的 `demos` 模块，让课程页与实验页职责清晰分离：

- `courses` 只负责课件叙事、知识组织和 slide 节奏
- `demos` 只负责可运行实验、输入输出反馈和操作体验
- 两者通过明确的“实验入口页”建立连接，而不是通过 `iframe` 嵌套

## 3. 设计原则

### 3.1 单一职责

- 课件页不再直接承载真实 demo
- 实验页不再伪装成 slide

### 3.2 统一结构

未来 `Week 4` 的 `JSON / XHR / fetch / Promise / async-await` 都使用同一套路由和页面骨架，不再一节一个特殊处理。

### 3.3 渐进迁移

第一阶段不要求把所有 demo 重写成 React 页面。已有 `public/course-demos/week4/*.html` 可以先复用，先完成“路由层统一”和“课程页解耦”。

## 4. 目标结构

### 4.1 路由职责

课程模块继续保持：

- `/courses`
- `/courses/week-4`
- `/courses/week-4/data-interchange`

新增通用 demos 模块：

- `/demos`
- `/demos/week-4/json/stringify-parse`
- `/demos/week-4/json/localstorage`

后续可继续扩展：

- `/demos/week-4/xhr/...`
- `/demos/week-4/fetch/...`
- `/demos/week-4/promise/...`
- `/demos/week-4/async-await/...`

### 4.2 页面角色

#### Courses 页面

负责：

- 本周知识点主线
- 概念解释
- 代码示例
- 课件式翻页

不负责：

- 大面积交互式演示
- 长时间停留的实验操作
- 输入输出日志面板

#### Demos 页面

负责：

- 实验说明
- 可运行演示
- 输入、输出、日志
- 明确的“观察点”提示
- 返回课程或切换相邻 demo

## 5. 课程页中的 Demo 形态

现有 `demo slide` 将不再展示 `iframe`。

它会被调整为一种“实验入口页”，承担的是过渡与引导，而不是运行 demo 本身。

### 5.1 实验入口页包含的信息

- 实验标题
- 该实验验证什么
- 推荐观察点（2-3 条）
- 一个主按钮：`打开实验`
- 一个辅助信息区：提示该实验属于哪个 week / lesson

### 5.2 用户路径

推荐路径如下：

1. 用户在 `courses` 中阅读知识点
2. 翻到实验入口页
3. 点击 `打开实验`
4. 跳转到独立 `demos` 页面进行操作
5. 从 demos 页面点击“返回课件”
6. 回到原课程知识点继续阅读

这样课程叙事与实验操作彼此独立，但在学习路径上仍然连续。

## 6. Demos 模块页面骨架

第一阶段的 demos 页面应采用统一骨架，而不是直接裸露静态 HTML 文件。

### 6.1 页面结构

- 顶部：返回课程 / 当前实验标题 / 所属 week 与 lesson
- 中部主区域：实验内容承载区
- 辅助说明区：实验目标、建议观察点、快捷导航
- 底部或顶部次导航：上一个实验 / 下一个实验

### 6.2 视觉要求

- 延续当前系统的暖纸张底色与课程字体体系
- 比课件页允许更高密度，但不能回到“普通工具页”的冰冷感
- 返回课程按钮要明显，避免用户在 demo 中迷路

## 7. 数据模型调整

当前课程 slide 中的 demo 数据偏向内嵌：

- `demo.src`
- `demo.note`

调整后应转为“实验引用”模型。

建议结构：

```ts
demo: {
  route: '/demos/week-4/json/stringify-parse'
  ctaLabel: '打开 stringify / parse 实验'
  objectives: [
    '观察 parse 成功与失败的区别',
    '比较紧凑字符串和格式化字符串',
    '验证 stringify 会丢掉哪些值',
  ]
}
```

说明：

- `route` 是唯一跳转目标
- `ctaLabel` 用于课程页按钮文案
- `objectives` 用于课程页上的“你应该观察什么”

第一阶段如果需要兼容旧数据，可保留 `src` 作为 demos 页面内部的承载来源，但课程页不再直接消费它。

## 8. 第一阶段实现边界

第一阶段只做最必要的结构落地，不扩散到所有课件。

### 8.1 本阶段包含

1. 新建通用 `demos` 模块路由骨架
2. 为 `Week 4 / JSON` 接入两个独立实验页面
3. 将 `data-interchange` 中的 demo slide 改为实验入口页
4. 在 demos 页面中提供清晰的“返回课程”入口
5. 保留现有 `public/course-demos/week4/*.html` 作为第一阶段的实验内容来源

### 8.2 本阶段不包含

1. 不重写所有旧 HTML demo 为 React 组件
2. 不一次性迁移 `XHR / fetch / Promise / async-await`
3. 不设计完整的 demos 首页信息架构
4. 不引入复杂权限模型或收藏、历史记录等扩展功能

## 9. 推荐技术落点

### 9.1 路由

在 `src/app/(app)/` 下新增独立的 `demos` 路由组，保持与 `courses` 并列，而不是嵌在 `courses` 子路由之下。

推荐原因：

- 语义更清楚：`demos` 是系统级模块，不是课程页内部的一种视图
- 后续可以承接不同 week 的实验，不必依赖某个课程页面存在
- 页面布局可以独立演进，不受 `CoursePage` 的 slide 骨架限制

### 9.2 内容承载

第一阶段的 demos 路由页内部可以通过统一壳层承载现有静态 HTML：

- 要么在新路由中内嵌现有静态资源
- 要么通过统一页面包装后再指向已有 demo 文件

关键要求不是技术形式，而是对用户暴露出来的是统一的 `/demos/...` 路由，而不是零散的静态文件地址。

## 10. 风险与处理

### 10.1 风险：课程与实验脱节

如果只是把 demo 从课件里拿走，却没有清晰入口，用户会感觉内容被拆散。

处理：

- 保留实验入口页
- 在 demos 页提供明显的返回课程按钮
- 明确展示该实验属于哪个 lesson

### 10.2 风险：旧 HTML 风格不统一

现有 demo HTML 是独立演示文档，风格与课程页接近但并非完整模块化。

处理：

- 第一阶段先统一外层路由与入口
- 第二阶段再决定是否将高频实验逐步 React 化

### 10.3 风险：后续 week 迁移成本不清楚

如果没有统一命名和路径规范，后续 Week 4 其他实验会再次出现各自为政。

处理：

- 在第一阶段就确定 `/demos/week-x/topic/demo-name` 的路径规范
- 课程内容层统一引用 `route`

## 11. 验收标准

完成后应满足：

1. `courses` 页面中不再出现 demo `iframe`
2. `Week 4 / JSON` 的两个实验都能通过独立 `/demos/...` 路由访问
3. 课程页中仍然能看到清晰的实验入口与观察目标
4. demos 页面可以明确返回到课程页
5. 路由结构足以支撑后续 `XHR / fetch / Promise / async-await` 继续迁移

## 12. 推荐结论

推荐正式采用：

- `courses` = 纯课件
- `demos` = 纯实验
- 两者通过实验入口页衔接

这是当前项目里最稳定、最统一、也最适合继续扩张到整个 `Week 4` 的方案。
