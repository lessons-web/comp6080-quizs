## Q1 The app that mounts nothing（8 marks）
*React Fundamentals*

A small React app is split across `index.html` and `main.jsx`. The HTML page contains `<div id="app"></div>`, but `main.jsx` calls `createRoot(document.getElementById('root'))`. When the page loads the console shows `Uncaught Error: createRoot(...): Target container is not a DOM element.` and nothing renders. `screen.png` shows the blank page.

Supporting files: `index.html`, `main.jsx`, `screen.png`

**(a) [2 marks]** What does `document.getElementById('root')` return on this page, and why does `createRoot(...)` fail with it?

**Model answer:**

```text
The markup only has an element with id="app", so no element has the id `root`. `document.getElementById('root')` therefore returns `null`. `createRoot` needs a real DOM element to use as the container it will render into; given `null` it has nothing to attach to and throws `Target container is not a DOM element`.
```

**Marking criteria:**

```text
1 mark for identifying that `getElementById('root')` returns `null` because no element carries that id.
1 mark for stating `createRoot` needs a real DOM element as its container and throws when it gets `null`.
```

**(b) [3 marks]** Explain the relationship between the id written in the HTML and the `getElementById` call, and what the "root" container is for React.

**Model answer:**

```text
The `id` in the HTML names an element; `getElementById` looks that name up in the current document and returns the matching element, or `null` if none matches. The two strings must agree character for character — `app` and `root` are different names, so the lookup misses. The root container is the one existing DOM node that React takes over: React mounts its component tree inside it and re-renders into it. Everything React draws lives under that container, so when the lookup fails there is no place to mount and the app never starts.
```

**Marking criteria:**

```text
1 mark for explaining that the HTML id and the `getElementById` argument must match exactly.
1 mark for describing the root as the existing DOM node React mounts its component tree into.
1 mark for linking a failed lookup to there being no container, so nothing renders.
```

**(c) [3 marks]** Give the fix, and explain what happens if the module script runs before the target element exists.

**Model answer:**

```text
Make the two names agree — either change the HTML to `<div id="root"></div>` or change the call to `createRoot(document.getElementById('app'))` — then `root.render(<App />)` mounts into that element. If the module script runs before the element exists in the DOM, the lookup still returns `null` and the same error is thrown; the element must already be parsed when `createRoot` runs (place the script after the element, or use `defer` or a module that waits for the DOM).
```

**Marking criteria:**

```text
1 mark for making the id in the HTML and the lookup match (either side).
1 mark for showing `root.render(<App />)` mounts into that container.
1 mark for stating the element must already exist at run time, otherwise the lookup is `null` and mounting fails again.
```

## Q2 The count that forgets the click（8 marks）
*React Fundamentals*

`Counter.jsx` receives its value from the parent as a prop and tries to add to it inside the click handler by writing to `props.value`. Each click logs a larger number in the console, but the button label never changes, and any later render puts the old value back. `counter.png` shows the frozen label.

Supporting files: `Counter.jsx`, `App.jsx`, `counter.png`

**(a) [2 marks]** Why does the label stay the same after a click even though the console logs a larger number?

**Model answer:**

```text
The handler only writes to the `props` object of the current render; it never asks React to render again. React re-renders in response to state changes, and nothing here changed any state, so no new render happens and the visible label keeps the old prop value. The `console.log` shows the mutated object in memory, which is not what the screen is showing.
```

**Marking criteria:**

```text
1 mark for stating the handler never triggers a re-render because no state changed.
1 mark for stating the screen keeps the previously rendered value, so the log (a mutated object) differs from what is shown.
```

**(b) [3 marks]** Whose data is it, and what is a child component allowed to do with a prop it does not own? How is a child supposed to signal a change?

**Model answer:**

```text
The prop is the parent's data passed down read-only; the parent owns the value and the child only reads it. React's one-way data flow means a child must not modify a prop — props are a component's inputs, like function arguments. To change the value, the child calls a function the parent passed down (for example `onIncrement`), which changes the parent's state; the parent then re-renders the child with the new prop value. The child requests a change; the owner performs it.
```

**Marking criteria:**

```text
1 mark for stating the prop belongs to the parent and is read-only for the child.
1 mark for explaining one-way data flow: mutating a prop is not allowed.
1 mark for describing the child calling a parent-provided callback, so the owner updates state and re-renders with the new value.
```

**(c) [3 marks]** Rewrite Counter so it follows the contract, and explain why mutating props is a bug even when the number sometimes looks right.

**Model answer:**

```text
Give the parent a `useState` for the count and pass both the value and a callback: parent `const [count, setCount] = useState(0); <Counter value={count} onIncrement={() => setCount(count + 1)} />`; child `function Counter({ value, onIncrement }) { return <button onClick={onIncrement}>Count: {value}</button> }`. Now a click calls the parent's setter, state changes, and React re-renders with the new value. Mutating a prop is a bug because it edits another component's data without a re-render and desynchronises the DOM from the model; the number only "looks right" in a local log, until the next render overwrites it.
```

**Marking criteria:**

```text
1 mark for keeping the value in the parent's `useState`.
1 mark for passing a callback (e.g. `onIncrement`) that calls the parent setter.
1 mark for explaining that mutating a prop bypasses the re-render and desynchronises the model from the DOM.
```

## Q3 The card that was copied three times（8 marks）
*React Fundamentals*

`Card.jsx` hardcodes its body (a heading and a paragraph). The team also needed the same frame for a report panel and a tip panel, so they duplicated the whole component twice. A single border change now has to be made in three places. `cards.png` shows the three identical frames.

Supporting files: `Card.jsx`, `Home.jsx`, `cards.png`

**(a) [2 marks]** What is `props.children`, and what does it let Card do that a hardcoded body cannot?

**Model answer:**

```text
`props.children` is whatever you place between a component's opening and closing tags — the nested JSX React passes to the component as a prop. It lets the component own a fixed frame while the caller supplies the inside, so one Card can wrap a heading, a list, a form or a tip without being rewritten. A hardcoded body can only ever render the one thing written inside it.
```

**Marking criteria:**

```text
1 mark for defining `props.children` as the JSX placed between the component's tags.
1 mark for stating it lets the caller supply the content while the component keeps a fixed frame.
```

**(b) [3 marks]** Explain the separation of responsibility this creates, and what "composition" means here.

**Model answer:**

```text
Card becomes responsible only for the frame (border, padding, layout) and stays the same for every use; the caller becomes responsible for the content it passes in. This is composition: building bigger screens by nesting small, single-purpose components rather than by adding options or copy-pasting. Because the frame lives in one definition, a change to it appears everywhere it is used, and Card stays reusable for content it has never seen.
```

**Marking criteria:**

```text
1 mark for stating Card owns the frame and the caller owns the content.
1 mark for naming this "composition" (nesting small components to build bigger UI).
1 mark for noting the frame is defined once, so changes propagate and Card stays reusable.
```

**(c) [3 marks]** Rewrite Card to accept children, and show two different usages. Explain why this removes the copy-paste.

**Model answer:**

```text
`function Card({ children }) { return <section className="card">{children}</section> }`. Usage: `<Card><h3>New arrivals</h3><p>Six items</p></Card>` and `<Card><h3>Weekly report</h3><p>Sales are up 12%</p></Card>`. Both reuse the one Card, and the only difference lives at the call site. There is no second frame to maintain, so a border or spacing change is made once, and new content needs no new component.
```

**Marking criteria:**

```text
1 mark for a Card that renders `{children}` inside its frame.
1 mark for two usages that pass different children to the same Card.
1 mark for explaining that one definition removes the duplicate frames, so changes are made once and new content needs no new component.
```

## Q4 The badge that never turns red（8 marks）
*React Fundamentals*

`Badge.jsx` sets its look with an inline `style` object. `padding: 6` takes effect, but `background-color` and `border-radius` do nothing — every badge keeps the browser default. `badge.png` shows a high-priority badge that ignored the red.

Supporting files: `Badge.jsx`, `theme.js`, `badge.png`

**(a) [2 marks]** Why does `padding: 6` apply but `background-color` does not?

**Model answer:**

```text
React's `style` prop is a JavaScript object, and its keys must be the JavaScript property names (camelCase), so `padding` is a valid key and is applied. `background-color` is a CSS property name, not a JavaScript one; React does not recognise that key, skips it, and warns `Unsupported style property background-color. Did you mean backgroundColor?` in development. The declaration is dropped, so the background never changes.
```

**Marking criteria:**

```text
1 mark for stating the style object uses JavaScript (camelCase) property names, so `padding` is valid and applied.
1 mark for stating `background-color` is not a recognised key, so it is ignored (with a warning).
```

**(b) [3 marks]** Why are the keys JavaScript property names rather than CSS property names, and what does React do with a key it does not recognise?

**Model answer:**

```text
In an inline style React does not write CSS text; it sets properties on the element's `style` object in JavaScript, and that object's properties are camelCase (identifiers cannot contain dashes). So React expects `backgroundColor`, `borderRadius`, `fontSize`, and so on. When it meets an unknown key it cannot map it to a `style` property, so it ignores the declaration — the element keeps its previous value — and logs a warning in development. The style silently "does not work" rather than throwing.
```

**Marking criteria:**

```text
1 mark for explaining that React sets properties on the JavaScript `style` object, whose properties are camelCase.
1 mark for naming the correct keys (e.g. `backgroundColor`, `borderRadius`).
1 mark for stating an unknown key is ignored (with a warning), so the declaration silently has no effect.
```

**(c) [3 marks]** Rewrite the style so every declaration applies, and explain the rule for numbers.

**Model answer:**

```text
Use camelCase keys: `style={{ backgroundColor: level === 'high' ? 'red' : 'grey', borderRadius: 4, padding: 6 }}`. For numbers React appends `px` automatically for the length properties (so `padding: 6` becomes `6px` and `borderRadius: 4` becomes `4px`), which is why bare numbers are fine for them. A few unitless properties (such as `lineHeight`, `zIndex`, `opacity`, `flex`) take the number as-is, and other units can be given as strings, e.g. `width: '50%'` or `fontSize: '1.2rem'`.
```

**Marking criteria:**

```text
1 mark for the camelCase keys (`backgroundColor`, `borderRadius`).
1 mark for stating React appends `px` to numeric length values automatically.
1 mark for noting unitless exceptions (e.g. `lineHeight`, `opacity`) or giving other units as strings.
```

## Q5 The title style that fights itself（8 marks）
*React Fundamentals*

`Card.jsx` and `Button.jsx` each import a plain `.css` file, and both render `className="title"`. `Card.css` wants a large, dark title; `Button.css` wants a small, light one. Because the plain CSS is global, whichever file is imported last wins for both components. `page.png` shows the two titles looking identical.

Supporting files: `Card.jsx`, `Card.css`, `Button.css`, `page.png`

**(a) [2 marks]** Why do two components that both use `className="title"` end up sharing one style?

**Model answer:**

```text
A plain `.css` import is global: the selector `.title` is added to the whole document, not scoped to the file that imported it. So both components' elements match the same `title` rule set, and with equal specificity the declaration that appears later in the cascade wins for both. The class name is a shared global handle, so the two components cannot have different `title` styles.
```

**Marking criteria:**

```text
1 mark for stating a plain CSS import is global, so `.title` applies document-wide.
1 mark for stating equal specificity means the later rule wins for both components.
```

**(b) [3 marks]** How does a CSS Module change this, and why does it remove the clash?

**Model answer:**

```text
A CSS Module (a `*.module.css` file) rewrites each class name at build time into a unique, hashed name scoped to that file — for example `.title` becomes `.Card_title__a1b2c`. The component imports an object mapping the original names to the generated ones and applies `className={styles.title}`. Because the two files now emit different generated names, their rules can never collide even though both authors wrote `.title`; the class becomes local instead of global.
```

**Marking criteria:**

```text
1 mark for stating a CSS Module rewrites class names into unique, file-scoped (hashed) names.
1 mark for stating the component applies the name through the imported object (e.g. `styles.title`).
1 mark for explaining that different generated names remove the collision.
```

**(c) [3 marks]** Show how to import and apply the module for Card, and explain what the generated class name is.

**Model answer:**

```text
Rename the file to `Card.module.css` and import it: `import styles from './Card.module.css'`, then `<h3 className={styles.title}>...</h3>`. `styles` is an object whose `title` property is the generated name string; at build time the bundler replaces `.title` in the CSS with that name and gives you the same string in JavaScript. The element ends up with a unique class such as `Card_title__a1b2c`, so it only receives the Card title styles and never the Button's.
```

**Marking criteria:**

```text
1 mark for renaming to `*.module.css` and importing it as an object (`import styles from './Card.module.css'`).
1 mark for applying `className={styles.title}`.
1 mark for explaining the generated name is a unique, file-scoped string shared between the CSS and the JS.
```

## Q6 The same rule in three files（8 marks）
*Project Structure*

Three components each need to show a price in the shop's format, but instead of a shared helper each defines its own `formatPrice` inside the component body. `ItemCard.jsx` rounds to whole dollars, `Checkout.jsx` rounds to two decimals, and the receipt rounds differently again, so the same item shows three different prices. `prices.png` shows the mismatch.

Supporting files: `ItemCard.jsx`, `Checkout.jsx`, `prices.png`

**(a) [2 marks]** What problems come from defining the same rule as a helper inside each component body?

**Model answer:**

```text
Each copy is a separate definition, so they drift: one rounds to dollars, another to cents, and the same item shows different prices. The helper is also re-created on every render (a new function each time), and because it is trapped inside the component it cannot be imported or tested on its own. There is no single place to change the rule.
```

**Marking criteria:**

```text
1 mark for stating the copies drift, so the same input produces different results in different places.
1 mark for stating the helper is re-created each render and cannot be imported or tested on its own.
```

**(b) [3 marks]** Explain the intended responsibility of a component, a hook, and a util, and where this duplicated logic belongs.

**Model answer:**

```text
A component decides how something looks and returns JSX; it should not own business rules. A util is a pure function with no React or DOM access — the price formatting belongs in a util because it is plain input-to-output logic, importable and testable anywhere. A custom hook is reusable logic that uses React features (state, effects or memoisation) — the shared filter/sort belongs in a hook such as `useVisibleItems` when it needs those features, so both screens share one implementation. The rule of thumb: pure → util, React-dependent and shared → hook, rendering → component.
```

**Marking criteria:**

```text
1 mark for stating a component's job is rendering and it should not own business rules.
1 mark for placing the pure price formatting in a util (no React/DOM, importable and testable).
1 mark for placing shared React-dependent logic (e.g. filter/sort) in a custom hook.
```

**(c) [3 marks]** Show the split — a `formatPrice` util, a `useVisibleItems` hook and a component using both — and explain why each piece is now reusable.

**Model answer:**

```text
`utils/format.js`: `export function formatPrice(cents) { return '$' + (cents / 100).toFixed(2) }`. `hooks/useVisibleItems.js`: `export function useVisibleItems(items, query) { return useMemo(() => items.filter((i) => i.name.includes(query)).sort(...), [items, query]) }`. Component: `import { formatPrice } from '../utils/format'; import { useVisibleItems } from '../hooks/useVisibleItems'; const visible = useVisibleItems(items, query); return <li>{formatPrice(item.cents)}</li>`. Now there is one definition of each rule: `formatPrice` is pure and can be unit-tested on its own, `useVisibleItems` is shared by every screen that needs it, and the component only renders — a change to the rule is made in one file.
```

**Marking criteria:**

```text
1 mark for a pure `formatPrice` util exported from its own file.
1 mark for a `useVisibleItems` hook holding the shared derived logic.
1 mark for a component importing both and only rendering, with a reason each piece is now reusable / testable.
```

## Q7 The link nobody else can open（8 marks）
*Build and Delivery*

For a deliverable a student runs `npm run dev` and submits the printed address, `http://localhost:3000`, as the "deployed site". The marker opens it and sees nothing. `deploy.png` shows the terminal with the dev server running.

Supporting files: `package.json`, `deploy.png`

**(a) [2 marks]** Why does `http://localhost:3000` not work for anyone but the student's own machine?

**Model answer:**

```text
`localhost` means "this machine". The address only resolves to the student's own computer, where the dev server is running; on the marker's computer, `localhost` points at the marker's machine, where nothing is listening on port 3000. The site was never published anywhere others can reach, so there is nothing to open.
```

**Marking criteria:**

```text
1 mark for stating `localhost` refers to the viewer's own machine.
1 mark for stating the site was never published to a reachable host, so the marker's browser finds nothing.
```

**(b) [3 marks]** Explain what the dev server does that a production build does not, and why the dev server is not a delivery target.

**Model answer:**

```text
The dev server is a development tool: it compiles and serves modules on demand, keeps unminified, source-mapped output for fast rebuilds, and runs hot-module reload to update the page as you edit. It is optimised for feedback speed on your machine, not for serving many users. A production build instead bundles and minifies the code, strips development-only code, and writes self-contained static files meant to be hosted. The dev server is bound to your machine and is not intended to be the public site.
```

**Marking criteria:**

```text
1 mark for describing the dev server: on-demand compilation, unminified output, hot reload — built for development feedback.
1 mark for describing a production build: bundles and minifies into static output meant for hosting.
```

**(c) [3 marks]** Describe the correct way to deliver the site.

**Model answer:**

```text
Run the production build command (for example `npm run build`) to generate the optimised output (a `dist/` or `build/` folder). Then serve that generated output from a host — a static host such as Netlify, Vercel or GitHub Pages, or any web server pointed at the folder — and share that host's public URL. What you deliver is the built output, not the running dev server.
```

**Marking criteria:**

```text
1 mark for running the production build to generate the optimised output folder.
```

## Q8 The test that guards the class name（8 marks）
*UI Testing*

A button test asserts on the element's `className` and only that the element exists: `expect(button.className).toBe('btn-primary')`. When the design system renames the class to `button-primary` the test fails, although the button looks and works the same; meanwhile the test never noticed that clicking the button stopped updating the total. `test.png` shows the failing run and the still-correct button.

Supporting files: `Button.jsx`, `button.test.js`, `test.png`

**(a) [2 marks]** Why does asserting on the class name make the test brittle and unable to catch a real regression?

**Model answer:**

```text
The class name is an implementation detail — a styling handle that can change without any change to what the user sees or can do. Tying the test to the exact string means a harmless refactor (renaming the class) breaks the test, producing false alarms. At the same time it says nothing about behaviour, so a real bug — the click no longer updating the total — passes the test, because the class is still correct.
```

**Marking criteria:**

```text
1 mark for stating the class name is an implementation detail that can change without any user-visible change.
1 mark for stating that this makes the test fail on harmless refactors while missing actual behaviour bugs.
```

**(b) [3 marks]** Explain the difference between testing implementation details and testing user-visible behaviour, and which survives a refactor.

**Model answer:**

```text
An implementation test asserts on internals: class names, component names, internal state, or exact markup structure. A behaviour test describes what a user can see and do — the text on screen, an accessible name, or the result of clicking — which is the contract of the feature. Behaviour survives refactors because renaming a class, changing a wrapper element or moving code does not change the visible outcome, so the test keeps passing while still failing if the outcome actually breaks. Implementation tests tend to break on refactors and miss behaviour bugs at the same time.
```

**Marking criteria:**

```text
1 mark for defining an implementation test (class names, internal state, exact markup) versus a behaviour test (what the user sees or does).
1 mark for stating behaviour survives refactors because the visible outcome is unchanged.
1 mark for noting implementation tests break on refactors and miss behaviour bugs at the same time.
```

**(c) [3 marks]** Rewrite the test to assert what the user can see and do.

**Model answer:**

```text
Query by role and accessible name, then assert on the visible result: `const button = screen.getByRole('button', { name: /add to cart/i }); await userEvent.click(button); expect(screen.getByText('Total: $15.00')).toBeInTheDocument()`. The test no longer mentions the class, so a rename cannot break it; it checks the button's accessible name (also a small accessibility check) and that clicking actually updates the total, which is the behaviour a regression would break.
```

**Marking criteria:**

```text
1 mark for querying by role and accessible name instead of a class.
1 mark for performing a user action (clicking) and asserting on a visible result.
1 mark for explaining the test now survives a rename and would catch the total no longer updating.
```

## Q9 The page the crawler sees as empty（8 marks）
*Rendering Strategies*

A content page is a client-rendered single-page app: the server sends a shell whose only body content is `<div id="root"></div>`, and the text appears only after the JavaScript has downloaded and run. With JavaScript blocked (or before it finishes on a slow phone) the page looks empty, and the fetched HTML source contains none of the article. `source.png` shows the raw HTML the server returned.

Supporting files: `index.html`, `source.png`

**(a) [2 marks]** Why is the page empty before the JavaScript runs, and what does that mean for a crawler that does not run JavaScript?

**Model answer:**

```text
This is client-side rendering: the HTML the server sends is only a shell with an empty container, and the actual content is created in the browser by JavaScript after it loads. Until that script runs there is nothing in the DOM to show, so the user sees a blank page. Anything that reads the HTML without running the app's JavaScript — such as a crawler or a link-preview generator — sees only the empty shell, not the article.
```

**Marking criteria:**

```text
1 mark for stating the server sends only an empty shell and the content is built by JavaScript in the browser.
1 mark for stating that without running that JavaScript there is no content, so anything reading the HTML sees an empty page.
```

**(b) [3 marks]** Explain how SSR and SSG differ from CSR in where and when the HTML is produced, and one trade-off of each.

**Model answer:**

```text
With SSR the HTML is produced on the server for each request: the server runs the components and returns filled HTML, which then rehydrates into the interactive app in the browser — trade-off: it costs server work on every request and needs a server running. With SSG the HTML is produced once at build time and the same static file is served to everyone — trade-off: it is fast and cheap to serve, but the page is fixed at build time unless you rebuild, so it suits content that rarely changes. Both send real content in the first response, unlike CSR where content appears only after JavaScript runs.
```

**Marking criteria:**

```text
1 mark for SSR: HTML produced per request on the server (with rehydration).
1 mark for SSG: HTML produced once at build time and served as a static file.
1 mark for one trade-off of each (SSR: per-request server cost; SSG: content fixed until rebuild).
```

**(c) [3 marks]** Choose the right strategy for a marketing page whose content barely changes, and justify it.

**Model answer:**

```text
Use SSG. The page's HTML can be generated once at build time and reused for every visitor, so the first response already contains the full content and needs no JavaScript to be readable — good for crawlers and slow devices. Because the content barely changes, the usual downside of SSG (having to rebuild to update) rarely applies, and there is no per-request server-rendering cost.
```

**Marking criteria:**

```text
1 mark for choosing SSG.
1 mark for justifying it with prebuilt HTML served to everyone (readable without JavaScript).
1 mark for connecting the choice to the content barely changing, so the rebuild downside rarely matters.
```

## Q10 Lint switched off, bug shipped（8 marks）
*Tooling*

A student could not get the linter to pass, so they disabled it and kept coding. `npm run build` still succeeded, they submitted, and a review found a comparison written with `==` and a variable that was never used. `terminal.png` shows a green build next to a skipped lint step.

Supporting files: `eslint.config.js`, `package.json`, `terminal.png`

**(a) [2 marks]** Why does turning lint off not stop the build, and what kind of problems does that let through?

**Model answer:**

```text
Linting and building are separate steps. The build only needs the code to compile and bundle, so nothing runs the linter and the build still succeeds. Disabling lint lets through code-quality and hazard problems that are still valid JavaScript — for example a `==` comparison that coerces unexpectedly, an unused or misspelled variable, or a suspicious pattern — none of which make the build fail on their own.
```

**Marking criteria:**

```text
1 mark for stating lint and build are separate steps, so the build does not run the linter.
1 mark for giving the kind of problems that survive (valid-but-risky code such as `==` or an unused variable).
```

**(b) [3 marks]** Explain what lint is for versus what the build does.

**Model answer:**

```text
Lint is static analysis of source code: it reads the code without running it and flags patterns against a set of rules (style, common mistakes, likely bugs), quickly and per-line. The build compiles and bundles: it resolves imports, transforms JSX and produces the output files; it fails on hard errors such as a missing module or a syntax error, but it does not judge style or suspicious-but-legal patterns. Lint catches "this is legal but probably wrong"; the build catches "this cannot be turned into a working app".
```

**Marking criteria:**

```text
1 mark for describing lint as static analysis that flags risky patterns without running the code.
1 mark for describing the build as resolving imports and producing output, failing on hard errors (missing module, syntax error).
1 mark for the contrast: lint finds legal-but-wrong patterns; the build finds what cannot be compiled at all.
```

**(c) [3 marks]** Give one case only lint catches and one case only the build catches, and explain why you keep both.

**Model answer:**

```text
Only lint: a `==` where `===` was meant, or an unused variable — the code runs and the build is happy, but the pattern is a hazard lint flags. Only the build: an `import` of a file that does not exist, or a syntax error — no lint rule can produce a bundle, and the build fails because it cannot resolve or compile. Keep both because they cover different failures: lint guards the correctness and consistency of the source before it runs, the build proves the app can actually be produced and served. Turning lint off to silence it hides the first class of bugs without fixing them.
```

**Marking criteria:**

```text
1 mark for a case only lint catches (e.g. `==` misuse, unused variable).
1 mark for a case only the build catches (e.g. a missing import, a syntax error).
1 mark for explaining both are kept because they catch different failures and silencing lint hides bugs rather than fixing them.
```
