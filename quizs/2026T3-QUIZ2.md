*JavaScript and the DOM*

**Model answer:**

```text
The click lands on the `<span>`, so `event.target` is the span, which has no `data-action`. `event.target.dataset.action` is `undefined` and `runAction(undefined)` does nothing. The listener still runs, but the click's target is the wrong element for reading the data.
```

**Model answer:**

```text
Read the data from the element the listener is attached to, which is always the button: use `event.currentTarget.dataset.action`. Using `event.target.closest('button')`, or a variable that holds the button, is also accepted.
```

**Marking criteria:**

```text
1 mark for a correct fix using `currentTarget` or `closest('button')`.
```

**(c) [1 marks]** Instead of changing the listener, a teammate adds a second listener to the span: `document.querySelector('#save span').addEventListener('click', () => runAction('save'));`. The student clicks on the words. How many times does `runAction` run, and with what?

**Marking criteria:**


Supporting files: `form.png`, `index.html`, `profile.js`

**(a) [1 marks]** Explain why the message disappears and the form empties.

**Model answer:**

```text
Submitting a form has a default action: the browser sends the form and loads the page again. Calling `event.preventDefault()` in the handler stops this.
```

**Marking criteria:**

```text
1 mark for identifying the default submit / reload and linking it to the disappearing message and empty form.
```

**(b) [1 marks]** The teammate stops the reload, but also moves `const name = document.querySelector('#name').value;` to the top of the file, above the listener. The student types a name and presses Save, and still sees `Name required`. Explain why.

**Model answer:**

```text
The moved line runs once, when the script loads, and the box is empty then. `name` holds that text, which is a copy and is not linked to the box, so the handler keeps testing the old empty string however much the student types. The value has to be read inside the handler, when the form is submitted.
```

**Marking criteria:**

```text
1 mark for explaining that the value was captured once too early, before the user typed.
```

**(c) [1 marks]** With both problems fixed, the designer adds a second button inside the form, `<button id="clear">Clear</button>`, with a click listener that empties the name box. A student types a name and clicks Clear, and the message says `Name required`. Explain why.

**Model answer:**

```text
A button inside a form with no `type` is a submit button, so clicking Clear also submits the form. The click listener empties the box first, then the submit handler runs, reads the now-empty box and shows `Name required`. Giving it `type="button"` stops it submitting.
```

**Marking criteria:**

```text
1 mark for identifying the default button type as submit and linking that to the extra form submission.
```

## Q3.1 Export that freezes the page（6 marks）
*Async JavaScript: Event Loop and Promises*

A timetable admin page can export all 200,000 enrolment rows as a CSV file. A clock in the corner ticks every second, and a Cancel button is meant to stop an export that is running. Staff report that during an export the clock freezes and Cancel does nothing, and that `Cancelled` then appears after `Done`. The code, a screenshot of the page and a timeline of one export are below.

Supporting files: `export.png`, `timeline.svg`, `export.js`

**(a) [2 marks]** Using the timeline, describe why the clock stops ticking and why the Cancel click has no effect until the export has finished.

**Model answer:**

```text
JavaScript in the page runs one thing at a time, and the export click handler runs all the way to the end before anything else can start. The clock's timer callbacks and the Cancel click handler are not lost, but they wait in the queue until the export handler returns and the call stack is empty. Only then can the event loop run them, at about 4 seconds, which is why `Cancelled` appears after `Done` and the cancelled flag is set too late to stop anything.
```

**Marking criteria:**

```text
1 mark for explaining that the long export handler blocks the main thread.
1 mark for explaining that queued timer and click callbacks only run after the handler finishes.
```

**(b) [2 marks]** Describe, at a high level, one change so that the clock keeps ticking and Cancel works while an export is running, and say what the student would notice. You do not need to write code.

**Model answer:**

```text
Split the export into small chunks and schedule each next chunk with a timer instead of one long loop. Between chunks the queued clock ticks and Cancel click can run, so the clock keeps going and Cancel can stop the export. The export takes a little longer overall, but the page stays responsive.
```

**Marking criteria:**

```text
1 mark for a fix that yields back to the event loop, such as chunking the work.
1 mark for correctly describing the user-visible effect.
```

**(c) [2 marks]** A student gets impatient and clicks Export a second time, one second after the first click. With the current code, describe when the second click is handled and what the student ends up seeing.

**Model answer:**

```text
The second click is not lost, and it does not start a second export at the same time. It waits in the queue until the first click handler has finished, at about 4 seconds, and only then does its handler run. That starts a new export, so the page freezes again until about 8 seconds and the student effectively gets the file twice.
```

**Marking criteria:**

```text
1 mark for placing the second click after the first long handler completes.
1 mark for describing the resulting second export and extra freeze.
```
