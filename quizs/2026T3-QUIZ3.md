## Q1.1 Delete beside Edit（3 marks）
*UI Design Principles and User Experience Reasoning*

On the Qanda discussion site, the creator of a thread sees three buttons under it, as in the screenshot `thread.png`. Edit lets the creator change the thread. Delete removes the thread straight away and sends the user back to the dashboard. Like adds a like. Mei is the creator of this thread and wants to edit it.

Supporting files: `thread.png`

**(a) [1 marks]** What about the design of these three buttons makes it easy for Mei to press Delete by mistake?

**Model answer:**

```text
All three buttons look the same (same colour, size and style) and sit right next to each other with almost no gap, so nothing sets Delete apart from Edit and Like, and a slightly off click lands on the wrong one.
```

**Marking criteria:**

```text
1 mark for the identical styling and/or the tiny gap that gives no visual separation between Edit and Delete.
```

**(b) [2 marks]** Describe one change that makes an accidental delete less likely, and one different change that makes it less costly when it still happens.

**Model answer:**

```text
Less likely: ask "Delete this thread?" and wait for a confirmation before deleting; style Delete differently from the other buttons (for example red or outlined); or move or space Delete away from Edit and Like. Less costly: let the user undo the delete straight afterwards, or keep deleted threads somewhere they can be restored from.
```

**Marking criteria:**

```text
1 mark for a change that reduces the chance of the mistake (confirmation step, different styling, or moving / spacing Delete away).
1 mark for a different change that reduces the cost after the mistake (undo, or a place deleted threads can be restored from).
```

## Q1.2 An empty dashboard（3 marks）
*UI Design Principles and User Experience Reasoning*

`dashboard.png` shows the Qanda dashboard for a user who has just registered and has no threads yet. The only way to create a thread is the "+" in the header. In a usability test, 8 new users were asked to start a discussion. 5 said the page "was still loading" or "looked broken". The other 3 found the "+", but only after more than a minute.

Supporting files: `dashboard.png`

**(a) [1 marks]** Every tester's dashboard was working correctly, but they did not realise it. Why not, and what might they have expected to see that would show the page was working?

**Model answer:**

```text
The blank area below "Dashboard" looks the same whether the threads are loading, failed to load, or there are no threads. Nothing on the page tells these apart, so testers assumed the list had not arrived yet or had failed. They would have expected the page to say what state it is in: a message such as "You have no threads yet" once the list has loaded empty (or a "Loading..." indicator while it is still loading).
```

**Marking criteria:**

```text
1 mark for explaining that the blank area is indistinguishable from loading or failed, and for naming an explicit state message (an empty-state message, or a loading indicator).
```

**(b) [2 marks]** Describe how the "+" for creating a thread could be shown instead so that new users find it easily, and give an example HTML element, with CSS, for your idea. Inline CSS is accepted.

**Model answer:**

```text
Replace the small icon-only "+" with a clearly labelled button, such as "Create your first thread", placed in the empty area below "Dashboard" where new users are already looking. Style it as the main action on the page: larger, with padding and a filled background in the site's colour, so it stands out. The text label says what it does, so users do not have to guess what "+" means. For example: `<button style="padding: 12px 24px; font-size: 18px; background: #2b3a67; color: white; border: none; border-radius: 6px;">+ Create your first thread</button>`.
```

**Marking criteria:**


## Q2.1 A token that runs out of its comment（3 marks）
*HTML/CSS Layout and Responsive Behaviour*

On the Qanda thread page each comment is shown in a box. Ben pastes a long login token into his comment. The markup and styles are in `index.html` and `style.css`, and `comments.png` is a screenshot of the page.

Supporting files: `comments.png`, `index.html`, `style.css`

**(a) [1 marks]** Ben's sentence wraps onto new lines inside the box, but the token runs straight out of it. Why does the token not wrap too?

**Model answer:**

```text
The browser only breaks lines at places where it is allowed to, such as spaces (and hyphens). The token is one very long "word" with no spaces in it, so there is nowhere to break it. It is wider than the 360px box, and because the box has a fixed width it cannot grow, so the token overflows past its edge.
```

**Marking criteria:**

```text
1 mark for explaining that line breaks only happen at allowed break points (spaces / hyphens) and the token has none, so it overflows the fixed-width box.
```

**(b) [2 marks]** A teammate suggests adding `overflow: hidden` to `.comment`. Describe what Ben's comment would look like then, and give a better CSS fix with the reason it is better.

**Model answer:**

```text
With `overflow: hidden`, the overflow is removed, but the end of the token would be cut off at the right edge. Other users will not see or copy the whole token. A better fix is `overflow-wrap: anywhere` (or `overflow-wrap: break-word`, or `word-break: break-all`) on the comment text. It allows the browser to break inside a word when the word cannot fit on a line, so the token wraps onto several lines inside the box.
```

**Marking criteria:**

```text
1 mark for describing that `overflow: hidden` clips / cuts off the end of the token.
1 mark for a correct wrapping fix (`overflow-wrap: anywhere` / `break-word`, or `word-break: break-all`) with the reason that it lets the browser break inside the long word.
```

## Q2.2 Buttons that jump（3 marks）
*HTML/CSS Layout and Responsive Behaviour*

A Qanda post contains a 600 by 300 pixel sketch, with Reply and Like buttons underneath. The markup and styles are in `index.html` and `style.css`. Mei is on slow Wi-Fi. `loading.png` shows the page just after it appears, and `loaded.png` shows it about two seconds later, after the sketch has downloaded. Mei went to click Reply as soon as the page appeared, but her click landed on the sketch.

Supporting files: `index.html`, `loading.png`, `loaded.png`, `sketch.png`, `style.css`

**(a) [1 marks]** Why do the Reply and Like buttons move down when the sketch finishes downloading?

**Model answer:**

```text
The `<img>` tag does not define the picture's size, so the browser does not know its size until the file is downloaded. Until then it gives the image no space, and the buttons just sit under the text. When the 600 by 300 picture arrives, the browser makes room for it and pushes everything below it down by about 300px.
```

**Marking criteria:**

```text
1 mark for explaining that the `<img>` has no declared dimensions, so no space is reserved until the download finishes and the later layout shift pushes the buttons down.
```

**(b) [2 marks]** Describe a change to the page that stops the buttons from moving, and explain why it works.

**Model answer:**

```text
Add the picture's size to the tag: `<img src="sketch.png" width="600" height="300" alt="...">`. The browser then knows how big the image will be before the file arrives, so it reserves a 600 by 300 box straight away. The buttons start in their final position and nothing moves when the picture appears.
```

**Marking criteria:**

```text
1 mark for setting explicit `width` and `height` (or `aspect-ratio`) on the `<img>`.
1 mark for explaining that the browser can then reserve the space before the image loads, so nothing shifts.
```

## Q3.1 Helpers for the register page（3 marks）
*JavaScript and the DOM*

The Qanda team keeps two helper functions for the register page in `helpers.js`. `parseReply` turns the server's JSON reply into a list of thread titles. `showError` puts a message into the page's error popup. In the page, `helpers.js` is loaded with a script tag in the `head`, above the `div` with the id `error-container`. `runtime-order.svg` shows the Node test calls and the browser's document order.

Supporting files: `helpers.js`, `runtime-order.svg`

**(a) [1 marks]** The team wants to check these functions automatically with Node, without opening a browser, by calling each one with test input. One function can be checked this way and the other cannot. Which one cannot, and why?

**Model answer:**

```text
`showError` cannot. `parseReply` only uses `JSON.parse` and `map`, which are part of the JavaScript language and so work in any runtime, including Node. `showError` uses `document`, which is added by the browser and does not exist in Node, so calling it stops with "document is not defined".
```

**Marking criteria:**

```text
1 mark for naming `showError` and explaining it uses the browser-only `document` object, which Node does not provide.
```

**(b) [1 marks]** On the register page, a teammate adds the line `showError('Welcome back')` at the bottom of `helpers.js` so that it runs as soon as the file loads. What happens on the page, and why?

**Model answer:**

```text
The call fails with an error ("Cannot set properties of null") and no message appears. The script is in the head, so it runs before the browser has built the page body. The `error-container` div does not exist yet, so `getElementById` returns `null` and there is nothing to put the text into.
```

**Marking criteria:**

```text
1 mark for explaining that `getElementById` returns null because the head script runs before the `error-container` div exists, so the call throws.
```

**(c) [1 marks]** Instead, the teammate leaves the script tag in the head and calls `showError('Passwords do not match.')` from the register form's submit handler. A user submits mismatched passwords. Does the message appear, and why?

**Model answer:**

```text
Yes, the message appears. The handler only runs when the user submits the form, long after the page has loaded, so by then the `error-container` div exists. Where the script tag sits matters only for code that runs immediately when the file loads.
```

**Marking criteria:**

```text
1 mark for explaining the message appears because the submit handler runs after the page has loaded, when `error-container` exists.
```

## Q4.1 Super like（6 marks）
*React State and Rendering*

Each Qanda thread shows its like count with two buttons. "Super like" is meant to add 2 likes. `page.png` shows the buttons for a thread with 12 likes. `LikeButtons.jsx` contains the code.

Supporting files: `LikeButtons.jsx`, `page.png`

**(a) [2 marks]** The thread has 12 likes. The user clicks "Super like" once. What number is displayed, and why?

**Model answer:**

```text
13. During this render `likes` is the constant 12. Both calls to `like` run `setLikes(likes + 1)` with that same 12, so both ask React to set the value to 13. The second call does not see the first call's result.
```

**Marking criteria:**

```text
1 mark for stating 13.
1 mark for explaining both calls read the same 12 and both request 13, so the second does not add on top of the first.
```

**(b) [2 marks]** A teammate adds `console.log(likes)` as the last line of `superLike`. What does it print on that click, and why?

**Model answer:**

```text
12. Calling `setLikes` does not change the `likes` variable inside the function that is already running; it asks React to render again with the new value. Only the next render's `likes` is 13.
```

**Marking criteria:**

```text
1 mark for stating 12.
1 mark for explaining that `setLikes` schedules a re-render rather than changing the current `likes` variable.
```

**(c) [2 marks]** Describe a change so that both buttons work as described, and explain why it works.

**Model answer:**

```text
Change `like` to use the updater form: `setLikes(prev => prev + 1)`. React runs queued updaters one after another, passing each one the result of the previous one, so two calls give 12 → 13 → 14. Also accepted: `superLike` calls `setLikes(likes + 2)` directly, with the explanation that a single update from the current value is correct.
```

**Marking criteria:**

```text
1 mark for the updater form `setLikes(prev => prev + 1)` (or `setLikes(likes + 2)` in `superLike`).
1 mark for explaining that the updater form chains the calls so the second sees the first's result.
```

## Q5.3 An async effect callback（6 marks）
*React Effects and Data Flow*

`OrderPanel.jsx` loads an order summary. React prints a warning when the effect runs, and a failed request leaves the loading message on screen.

Supporting files: `effect-warning.svg`, `OrderPanel.jsx`

**(a) [3 marks]** OrderPanel has two symptoms: React warns about the function passed to `useEffect`, and a failed request leaves "Loading order..." on screen. What separate cause produces each symptom?

**Model answer:**

```text
An `async` function returns a Promise, so the function passed to `useEffect` returns a Promise. React expects that function to return nothing or a cleanup function. Separately, a failed fetch or JSON parse jumps past `setLoading(false)`. The code has no failure handling, so loading remains true.
```

**Marking criteria:**

```text
1 mark for explaining that the `async` callback returns a Promise instead of nothing / cleanup.
1 mark for explaining that a failed request skips `setLoading(false)`.
1 mark for linking the missing failure handling to the loading message staying on screen.
```

**(b) [3 marks]** How should the effect be reorganised so it can keep the `await` style, turn loading off after success or failure, and stop an older order request from updating the panel?

**Model answer:**

```text
Pass a regular function to `useEffect`, then define and call an async function inside it. That inner function can use `try` for the request, `catch` to store an error, and `finally` to turn loading off. The effect's cleanup should abort the older request or mark it as unable to update state. The async function should change `order`, `error`, or `loading` only for the current `orderId`.
```

**Marking criteria:**

```text
1 mark for a non-async effect that defines and calls an async function inside.
1 mark for `try` / `catch` / `finally` that always clears loading.
```

## Q6.3 Profile pages（6 marks）
*React Router and URL State*

The Qanda app has profile pages. `/profile/:name` shows that user's profile, and the "My profile" link in the navbar goes to `/profile`. `profile-pages.svg` shows the dashboard navbar and the profile page layout. `Profile.jsx` contains the code.
