你在浏览器里输入一个网址、点一次搜索，背后其实是**两台机器之间的一次对话**：你的设备发出请求，远处的服务器算完再把结果送回来。这一篇把「客户端-服务器模型」和建立在它之上的 **AJAX** 讲清楚，并解释为什么「延迟」与「吞吐」始终是一对拉锯的矛盾。

## 1. 客户端与服务器：谁是谁

| 角色 | 是什么 | 例子 |
|---|---|---|
| 客户端 Client | 用户直接使用的设备 | 智能手机、笔记本电脑 |
| 服务器 Server | 数据中心里成排的机器 | datacentre 里的机架（racks of machines） |

关键区别：客户端**主动**发起请求，服务器**被动**等待请求。客户端数量极多而分散，服务器相对集中但单体能力强。

## 2. 一次请求-响应循环

一次完整交互可以拆成「请求」和「响应」两半。以在搜索引擎里搜 cats 为例：

```text
客户端：发起请求  →  GET https://duckduckgo.com/ac/?q=cats
                        │
                        ▼
服务器：校验参数 → 执行 API → 返回数据
                        │
                        ▼
服务器：返回 payload  { "autocomplete": ["cats", "catsis"] }
                        │
                        ▼
客户端：收到 payload → 渲染 HTML/CSS → 执行 JS
```

- **请求阶段**：客户端带着参数（这里是 `q=cats`）向服务器提出请求。
- **服务器侧**：等待请求、**校验参数**、**执行对应 API**、**返回数据**。
- **响应阶段**：客户端**接收 payload**，渲染 HTML 与 CSS、执行 JS，把结果呈现在屏幕上。

> ⚠️ 常见误区：把「渲染页面」当成服务器的事。在现代前端里，服务器通常只返回**数据（payload）**，把 HTML/CSS 渲染与 JS 执行都交给客户端。

## 3. 现实不是一对一：多客户端对多服务器

真实的 Webapp 往往同时依赖多个 API，同时又被多个客户端访问：

```text
Webapp #1 ─┐                 ┌─→ Super cool cats API
           ├─ 请求 / 响应 ───┤
Webapp #2 ─┘                 └─→ Latest News API
```

- 一个 Webapp 会**同时面对多个 API**（例如「猫咪 API」与「新闻 API」）。
- 多个客户端会访问**多个服务器**，构成一个「多对多」的拓扑。

所以系统设计不能只考虑「一次对话」，而要同时扛住**大量并发交互**。

## 4. 延迟 vs 吞吐：一对核心矛盾

客户端与服务器关心的指标并不一样，甚至互相拉扯：

| | 客户端侧 | 服务器侧 |
|---|---|---|
| 核心指标 | **低延迟 latency** | **高吞吐 throughput** |
| 原因 | 交互与响应速度最重要 | 至少要扛住成千上万条请求 |
| 附加诉求 | 页面尽量一次、快速加载完 | 时间、电力、机器数量都很昂贵 |
| 坏体验示例 | 刷新后丢失页面滚动位置 | 请求一多就排队、整体变慢 |
| 扩展方式 | —— | 最大化吞吐，水平加机器 |

> ⚠️ 常见误区：以为「服务器越快，用户就觉得越快」。服务器忙着堆吞吐（每秒处理多少请求），不代表**单次**往返的延迟就低；用户感受到的是**延迟**，平台承受的是**吞吐**，两者要分别优化。

## 5. 客户端-服务器架构演进简史

| 阶段 | 客户端 | 渲染方式 | 扩展方式 |
|---|---|---|---|
| 1990s 与 2000s 早期 | 以桌面浏览器为主 | 静态网页，服务端渲染（SSR） | 升级单台服务器（垂直扩展） |
| 2000s 中期 – 2010s 早期 | 仍以桌面浏览器为主 | JS 带来更多客户端交互 | 仍以垂直扩展为主 |
| 约 2010s 至今 | iPhone 带来智能手机时代，客户端扩展到 IoT 与移动设备 | 几乎全部在客户端渲染 | 云托管为主，水平扩展 |

主线很清楚：**渲染责任从服务器逐步转移到客户端，扩展方式也从「把一台机器升级」变成「加更多机器」。**

## 6. 针对延迟与吞吐的解决思路

两类目标对应两套手段：

| 侧 | 思路 |
|---|---|
| 客户端侧（降延迟） | 把展示严格交给前端；首屏只带**必要的最小数据**；需要时再**异步按需拉取（lazy-loading）** |
| 服务器侧（提吞吐） | 用**异步事件处理**；等待 I/O 时去服务下一个请求，**绝不空闲**；通过**加服务器 + 负载均衡**横向扩容 |

要点：客户端**别一次要太多数据**，服务器**别在等待时干等**。

## 7. AJAX 到底是什么

**AJAX = Asynchronous JavaScript And XML**，它**是一组用来构建异步 Web 应用的技术集合，而不是某一项具体技术**。

- ✅ 它能带来：**离线应用**（offline apps）、**顺滑的 UI/UX**、**前端与后端解耦（modular frontend & backend）**。
- ❌ 它不是某个库、某个函数名，也不是必须使用 XML。

> ⚠️ 常见误区：看到名字里的 XML，就以为 AJAX 一定要用 XML。名字是历史遗留，**如今 JSON 比 XML 更常用来承载数据**——真按现在的情况，或许该叫「Ajaj」，只是念起来不够顺口。
