JavaScript 天生是单线程的，却要同时应付计时器、网络请求、用户点击等一大堆「同时进行」的事。支撑这一切的，就是**事件循环**。理解它之前，得先弄清「同步」和「异步」到底差在哪里，以及 JavaScript 为什么选择了协作式多任务而不是抢占式多任务。这篇是本周的概念地基。

## 1. 同步编程：一条直线走到底

**同步编程（Synchronous Programming）** 的特征非常朴素：

- 程序**自上而下**执行；
- **保证前一条指令完全结束**之后，才执行下一条；
- **极易推理**：读代码的顺序，就是实际执行的顺序。

代价是：只要某一步很慢（比如等网络返回），整条流程就被卡住，后面的代码一律不能动。

## 2. 异步编程：多条控制流

**异步编程（Asynchronous Programming）** 引入了**多条控制流**，也就是所谓「线程（thread）」：

- 多个线程可以**交错执行**，甚至**同时运行**；
- 换来的是吞吐与响应性；
- 代价是**难推理**：代码写的顺序，不再等于实际发生的顺序。

| 维度 | 同步 | 异步 |
|---|---|---|
| 控制流 | 只有一条 | 多条（线程） |
| 执行顺序 | 自上而下、严格串行 | 可交错、可并行 |
| 可推理性 | 高 | 低 |
| 典型瓶颈 | 一步慢则全线卡住 | 需要处理竞态与时序 |

> ⚠️ 常见误区：把「异步」等同于「更快」。异步本身不加速任何计算，它的价值在于**让慢操作不挡住其他工作**。

## 3. 用一条时间线看清差别

假设流程 A 在执行途中需要 B 帮忙。两者的差别可以这样画：

```text
同步：
A ──▶ [ 等 B 做完，A 什么都干不了 ] ──▶ B 完成 ──▶ A 继续
              （A 被阻塞的这段时间）

异步：
A ──▶ 把活交给 B ──▶ A 立刻继续做别的 ──▶ …未来某刻… ──▶ 拿到 B 的结果
                        （A 没有被阻塞）
```

- **同步**：A 先执行，**等 B 结束**，再继续。
- **异步**：A 先执行，**让 B 去做它的事**；B 在干活的同时，A 也在继续；未来某个时刻，A 收到 B 的结果。

## 4. 两种并发模型

并发并不是只有一种玩法，主要有两个模型：

| 模型 | 做法 | 擅长 | 本课关注度 |
|---|---|---|---|
| 抢占式多任务（pre-emptive multitasking） | 代码在**不同 CPU 核心上真并行** | CPU 密集型 | 不关心 |
| 协作式多任务（co-operative multitasking） | 待办任务**排队进循环**里依次执行 | IO 密集型 | 核心 |

- **抢占式多任务**：真的多核并行，适合 CPU 密集型负载，但调度复杂，**不是本课重点**。
- **协作式多任务**：任务排好队，在一个循环里被取出执行；它适合 IO 密集型负载，同时**兼具异步的收益与同步的可推理性**——因为每个任务自己都是同步跑完的。

## 5. JavaScript 采用的是协作式多任务

JavaScript 的选择是**协作式多任务**，具体表现为：

- 需要完成的任务就是**「事件」**；
- **事件处理器（event handler）**由**事件循环（event loop）**调度执行；
- **每个事件处理器都同步执行到完成**——中途不会被别的处理器插队。

也就是说：单看某一个事件处理器，它的行为和同步代码一样好推理；是「处理器之间的调度」提供了异步能力。

## 6. 事件循环的四个步骤

每个 JS 引擎大致遵循下面这套流程：

1. **自上而下执行脚本**，并把过程中遇到的处理器（handler）注册好；
2. **在循环里等待事件**；
3. 如果**有事件到来且存在对应处理器**，就把处理器**执行到完成**；
4. **回到第 2 步**，无限循环下去。

```text
1. 执行脚本、注册 handler
        │
        ▼
2. 循环等待事件  ◀─────────────────┐
        │                         │
        ▼                         │
3. 有事件且有 handler → 执行到完成 ──┘
        │
        ▼
4. 回到第 2 步（永不停止）
```

## 7. 浏览器替我们做的事

事件循环本身不负责计时、也不负责网络。这些是**浏览器**在幕后干的：

- **计时器倒数**（到点了才触发）；
- **网络请求**（真正发出去、等响应）；
- **把事件加入事件队列（event queue）**。

```text
[ 事件队列 ] ──▶ [ 事件循环 ] ──▶ [ 事件处理器 ]
  timers /        从队首取一个       同步执行到完成
  网络 / 点击      事件并调用它
        ▲
        │  浏览器在后台把新事件
        └── 追加进队列
```

## 8. 单线程的代价：阻塞事件循环

关键约束：**事件循环跑在单线程上**。这意味着——

- **长时间运行的处理器会阻塞其他一切**；
- 页面表现为**无响应**（点击没反应、动画卡死）。

```text
时间 ──▶
[handler 被调用] ──── 无事可做（其他事件全被挡住） ──── [handler 结束]
                       ▲
                       └─ 这段期间页面「冻住」
```

> ⚠️ 常见误区：写一个耗时几秒的循环来「算数据」，以为只是慢一点。实际上它会把整个事件循环钉死，期间**任何**点击、定时器、网络回调都无法执行。

## 9. 避免阻塞的两条建议

结合上面的模型，课程给了两条硬性建议：

- **所有网络请求一律异步**：不要用会阻塞的方式等待响应；
- **CPU 密集型计算推到后端服务器**去处理：把重活交给另一台机器，别占着事件循环。

只要遵守这两条，页面就能保持「随时可以响应新事件」的状态。
