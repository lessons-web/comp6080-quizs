声明式的代价是：React 必须替你算出「从旧界面到新界面」到底要动哪些 DOM。如果每次变化都把整个页面推倒重建，性能会崩。虚拟 DOM 就是 React 用来既**保持声明式的简单**、又**避免无谓 DOM 操作**的核心机制。这篇是本周最重的一篇。

## 1. 第一性问题：更新真实 DOM 为什么昂贵

浏览器渲染页面的流水线大致是：

```text
HTML/CSS 解析 → 构建渲染树 → layout（布局/回流）→ paint（绘制）→ composite（合成）
```

- `layout` 阶段要**计算每个元素的几何位置与尺寸**；HTML/CSS 的 layout 引擎很擅长**自适应**（窗口变了自动重排）。
- 但**频繁、零散地改动 DOM** 会反复触发 **layout 重算（reflow）**，单次也许不快，**累加起来非常慢**。
- 尤其当一次逻辑改动牵连多个元素时，浏览器可能被迫**多次**重排。

> 术语对照：layout（布局/回流）/ reflow（重排）/ virtual DOM（虚拟 DOM）/ diff / reconciliation（协调）/ surgical update（外科式更新）。

## 2. 朴素方案：整体重建 DOM

一个「逻辑上完全正确」的做法是：**任何变化发生时，删掉整棵 DOM，按新状态重新建一遍**。

- ✅ 优点：**无需考虑任何状态转换** —— 不用推导「从旧到新要改什么」，直接照着新状态生成即可，正确性极容易保证。
- ❌ 缺点：**开销过大**。哪怕只多了一个小元素，也要销毁并重建整棵树，触发海量 layout 重算。

也就是说：朴素方案把「状态转换」的复杂度换成了「性能」的代价。我们需要的是一个**既简单又高效**的中间层。

## 3. 关键洞察：更新时其实不关心布局

真正昂贵的不是「描述界面」，而是「让浏览器按描述去计算布局」。而**在计算差异的阶段，我们并不需要真实的布局信息**。

那么：能不能先用一个**廉价的、纯 JS 的对象树**来表示界面，在它上面比较差异，最后只把**最小差异**应用到真实 DOM？这正是虚拟 DOM 的思路。

## 4. 虚拟 DOM：四步走

**虚拟 DOM（Virtual DOM）** 是 React 在内存中维护的、用 JS 对象描述的「HTML 层级副本」。更新流程分四步：

| 步骤 | 做什么 |
|---|---|
| 1. 保留副本 | 在 JS 中保留一份 HTML 层级的**副本**（虚拟 DOM 树）。 |
| 2. 在副本上改动 | 状态变化时，生成一棵**新的虚拟 DOM 树**，改动只发生在 JS 对象上，**不碰真实 DOM**。 |
| 3. Diff | 对比新旧两棵虚拟 DOM 树，算出**最小差异集合**。 |
| 4. 外科式更新 | 只把差异对应的操作（插入/删除/更新）应用到**真实 DOM**，而非重建整棵树。 |

```text
状态变化
   │
   ▼
[生成新虚拟 DOM 树]  ──在 JS 对象层面，零 layout 开销
   │
   ▼
[Diff 新旧两棵树]    ──找出「哪里不一样」
   │
   ▼
[最小 DOM 操作]      ──只改差异处，尽量一次 layout 搞定
```

## 5. 举个例子：只多了一个 `<div>`

假设界面从 State1 变到 State2，**唯一的区别**是多了下面这一个节点：

```html
<!-- State2 相比 State1，只多这一行 -->
<div class="notice">新消息</div>
```

- **朴素方案**：删掉整棵树 → 重新创建所有节点 → 重新 layout。开销与**整页复杂度**成正比。
- **虚拟 DOM 方案**：Diff 发现只有一处差异 → 只在真实 DOM 上**调用一次插入**。开销只与**变化量**成正比。

界面越复杂、变化越小，虚拟 DOM 的优势越明显。

## 6. Diff 的约束：它并不做「最优解」

Diff 不是穷举所有编辑路径去求最小操作集（那是昂贵的图同构问题）。React 采用**启发式（heuristic）**策略，牺牲理论最优换取工程可行：

- **同层比较**：默认只比较树的**同一层级**，不跨层匹配。
- **类型不同即重建**：类型/标签不同，直接替换该子树，不再往下比。
- **用 `key` 辅助列表匹配**：列表项有稳定 `key` 时，React 能识别「哪些是同一个元素」，从而正确复用。**列表渲染务必给 `key`**，这也是 Diff 相关的高频考点。

```jsx
// ✅ 用稳定且唯一的 key，帮助 Diff 正确复用节点
{items.map((item) => (
  <li key={item.id}>{item.name}</li>
))}
```

## 7. 两个必须澄清的误区

> ⚠️ 误区一：**以为虚拟 DOM 让 DOM 变快了**。实际上 DOM 本身的速度没变，虚拟 DOM 的价值在于**减少不必要的 DOM 操作**——它把「整树重建」变成「只改差异」。

> ⚠️ 误区二：**以为虚拟 DOM 是浏览器的能力**。它是**框架自建的一层抽象**（在 `react-dom` 里实现），浏览器原生并不存在「虚拟 DOM」这种东西。

补充：虚拟 DOM 不是 React 独有，其他框架也有类似机制；它的核心收益是**声明式编程 + 可预测的批量更新**，而非「魔法加速」。

## 8. 完整闭环回顾

```text
render（生成虚拟 DOM）
   │
   ▼
状态变化 → 生成新虚拟 DOM
   │
   ▼
Diff 新旧两棵树 → 得到差异
   │
   ▼
外科式更新真实 DOM → 触发一次 layout → 屏幕更新
```

## 9. 自查清单

- ✅ 能解释「更新真实 DOM 昂贵」的根因是 **layout 重算**。
- ✅ 能说出朴素「整树重建」方案**逻辑正确但开销大**。
- ✅ 能按顺序背出虚拟 DOM 四步：副本 → 副本上改动 → Diff → 外科式更新。
- ✅ 能用「只多一个 `<div>`」的例子说明为何只插入一次而非重建。
- ✅ 明确虚拟 DOM **不给 DOM 加速**、且**不是浏览器能力**。
- ✅ 知道列表渲染要给稳定的 `key`，否则 Diff 会错误复用节点。
